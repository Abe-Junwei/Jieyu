# 项目、资料与持久化架构改进方案（修订四）

> **约束（D9，2026-10-08 19:22，用户）**：「整个项目都没有历史数据，没有向后兼容的需求」。
>
> 修订四按这条约束改写修订三：去掉所有为旧数据和旧格式保留的兼容设计，并建议把 schema 重置为一个基线。决定记录见 10.1，其中 D1–D8 各自标明了“有效 / 简化 / 作废”。修订二的外部评审核查见[核查结论](../audits/project-file-plan-rev2-review-verdict-2026-10-08.md)。本文仍是待实施方案。

## 1. 目标与状态

解语是本地优先的田野语言资料研究工作台，要长期保存录音、说明标注来源、可靠协作，并与外部工具交换资料。

**依据**
- 审查草稿（F1–F8）。
- 2026-10-08 对 `origin/main@85ff9f82` 的代码调查（功能分支的数据层与它相同）。
- 同类产品调研。
- 外部评审。
- D9 约束。

**本文的写法**
- 当前代码的事实和目标设计分开写。
- 标“已复现”的问题，都是在 fake-indexeddb 中复现的。

**D9 带来的两个变化**

1. **现在可以直接改 schema、ID 和格式，不需要迁移，也不需要兼容层。** 旧的 Dexie 版本历史、迁移代码、兼容分支都可以删掉。
2. **数据冻结点之前和之后，规则不同。**
   - 数据冻结点：第一批真实田野数据写入之前的那个时间点。
   - 冻结点之前：可以随时重置基线。
   - 冻结点之后：基线冻结，任何 schema 变化都必须走第 8 节的迁移安全机制。
   - 本文中凡写着“发布阻断”的事项，都必须在冻结点之前完成。

**成功标准**
- S1 同名资料不会被误覆盖。
- S2 改名、重载之后，关联关系不变。
- S3 删除录音后时间轴保留；恢复或导入不会抹掉本机的媒体字节和附件字节。
- S4 单个项目能连同依赖一起导出，并在空库中完整恢复。
- S5 失败或跳过不会被报告成成功。
- S6 已删除的项目不会复活。
- S7 代码边界能支撑以上行为。
- S8（新增）冻结点之后的每一次 schema 变化，都有恢复点和阻止策略。

**范围外**：更换 Dexie、微服务、monorepo、全仓目录搬迁、CRDT、通用文件管理器、完整的档案馆平台。

## 3. 成熟方案依据（压缩）

修订三第 3 节的依据仍然有效。这里只列出 D9 之后仍会用到的几条：

- **身份与名称分离**（OCFL、Logseq、Zotero）：来源和媒体使用 UUID，原名只作为元数据。
- **外部 ID 优先**：EAF 的 URN 用于文档级匹配；LIFT 的 guid 只用于词条级匹配。
- **Relink 与重新导入分开**（Lightroom、ELAN）。
- **出口分开并标明保真度，恢复默认生成新项目**（Logseq、FLEx）。
- **升级前留副本，只写副本**（Zotero、audacity-project-tools）：冻结点之后适用。
- **墓碑长期保留、冲突时删除优先、稳定的 ClientId**（Joplin、Lexbox、Harmony）。
- **persist 伴随用户手势请求；Safari ITP 风险措辞收窄；站点外备份**（web.dev、WebKit 2020/2023）。
- **Dexie**：事务里不能等待非 IDB 的异步调用；upgrader 一旦发布就冻结，冻结点之后适用。

结论：继续复用 Dexie 和 fflate，第 1、2 批不新增依赖。

## 4. 目标领域模型

### 4.1 概念与关系

| 对象 | 身份与职责（直接写进基线 schema） | 关系 |
| --- | --- | --- |
| Project 项目 | textId、元信息、默认访问级别 | 拥有资料组、标注文档、媒体、来源、项目目录 |
| MaterialGroup 资料组 | 一次采录事件 | 第 5 批落地；基线里可以先预留可选的 `groupId` 字段 |
| MediaResource 媒体 | UUID；原名、显示名、格式、大小、sha256、时长；`role: primary/derived`；**必填** `timelineKind: acoustic/placeholder`、`byteLocation: managed/url/none`、`availability: available/missing` | 不再有启发式推断；`derivedFrom` 记录派生关系 |
| AnnotationDocument 标注文档 | **基线即带** `documentId`；层归属于文档；文档引用来源 | 先只有一份 `default` 文档也可以；多文稿的 UI 放到第 5 批 |
| SourceRecord 导入来源 | **独立表** `source_records`；UUID；`originalName`、`displayName`、`format`、`byteSize`、`sha256`、`externalDocId?`、`importedAt`、`importBatchId`、`storedBytes` | 取代 `texts.metadata.sourceFiles`，没有 legacyId，也没有 `name` 兼容字段 |
| ProjectCatalog 项目目录 | 说话人、词条、正字法等；**`textId` 必填**（结构规则对应 `projectId`）；内置种子保留在代码里 | 跨项目复用的方式是“从其他项目导入”（复制并重映射 ID）；不存在无主行 |

### 4.2 规则

1. **来源身份**：一律使用 UUID。
2. **重新导入的匹配顺序**：
   1. EAF 的 URN 相同：判定为“更新已有文档”，先预览。
   2. sha256 相同：提示“内容相同”。
   3. 仅文件名相同：作为新来源，显示名自动加序号区分。
   4. LIFT 只做词条级匹配（guid 优先，没有 guid 时用 id），导出时补写 guid。
3. **哈希在事务外先算好**，再在事务里登记，写入后读回校验。
4. **媒体关联**：校验 mediaId 存在、且属于本项目；只有唯一候选时才提示匹配。
5. **写入边界**：提供 `patchProjectMetadata` 一类的事务原语；禁止对 texts 先 remove 再 insert；项目不存在时返回明确结果。
6. **导入**：主体、来源登记、清理都放在同一次提交里。
7. **入站字节语义**（适用于所有导入、恢复和协作 restore 路径）：
   - 新格式里，每个媒体行或附件行都必须显式声明 `bytes: included | omitted`；缺少这个声明就当作格式错误，**拒绝导入，不去猜**。
   - `omitted` 时：本机已有同一 id 的，**保留本机字节**；没有的，状态标为 `none + missing`。
   - 入站数据缺少字节，永远不能被理解为“删除字节”。
   - replace 类操作在删行之前，先读出需要保留的字节。
   - 不存在“未知或旧包”这一类情况，因为没有旧包。
8. **标注文档**：基线 schema 就带 `documentId`，层通过 `documentId` 归属到文档；manifest 包含 `documents[]`。这样第 3 批的包格式以后不需要因为多文稿而升级。
9. **目录归属在写入时强制**：
   - schema 把 `textId` 设为必填，service 在没有项目时拒绝写入。
   - 删除 `claimUnscopedCatalog` 以及各读路径上的调用，读操作不再产生任何写入。
   - 同时修订 ADR-0044 第 2 条。
   - 没有活动项目时，目录页面怎么处理，见 10.2 的 P2。
10. **Relink 与重新导入分开**：Relink 保持 MediaResource ID 不变。

### 4.3 元信息与访问

与修订三相同：
- 访问级别在 项目 → 资料组 → 文件 三层之间继承，下层可以覆盖上层；词表候选为 `open / registered / restricted / community-protocol`，外加 `embargoUntil`。
- 必填项只有 ID 和归属。
- 同意书、敏感身份、公开描述分开保存。

D9 之后，现有的 `accessRights` 字段可以直接按新词表改写，不需要过渡。

## 5. 操作与界面契约

| 操作 | 目标行为 |
| --- | --- |
| 首次导入、再次导入 | 内容和来源在同一次提交里写入；再次导入先显示覆盖预览；第 5 批起可以选择“作为新的标注文档加入”（D4） |
| 改名 | 只改 displayName |
| 挂接或替换媒体 | Relink 保持身份，或者显式创建派生资源；时长不一致时先预览 |
| 导入音频 | 只合并 `timelineKind = placeholder` 的行 |
| 删除录音字节 | 保留原名；状态变为 `acoustic + none + missing` |
| 删除项目 | 分“仅从本机移除”和“删除云端项目”两种；用可重试的清理任务执行；写项目墓碑；取消待发操作（第 9 节） |
| 导出 JYM / JYT / JYB | 按 D1 执行（7.1），不提供旧格式 |
| 导入 .jym / .jyt | 只走项目包流程，默认恢复为新项目；**不读取旧版整库包**，遇到时提示“格式不受支持”并拒绝 |
| 覆盖当前项目 | 只对从未协作过的本地项目提供（D5、D6）；需要二次确认，并自动做覆盖前快照 |
| 恢复 JYB | 两种模式（D7，见 7.4） |
| 从其他项目导入目录 | 复制并重映射 ID（D3） |
| 在没有活动项目时操作目录 | 见 P2（10.2） |

## 6. 持久化与代码组织

### 6.1 存储分类

| 数据 | 策略 | 备份与清理 |
| --- | --- | --- |
| 项目、内容、关系 | 新基线主库；用事务、校验边界、写后读回 | 进项目包和 JYB |
| 原始媒体与附件 | 状态字段必填；入站字节语义见 4.2-7 | JYM 默认带字节；JYT 不带；JYB 明确写出带不带 |
| 派生数据 | 可以重建 | 不进项目包 |
| 协作出站队列 | 显示 pending、failed、cancelled 三种状态 | 删除项目时标为 `cancelled_by_delete` |
| 恢复快照、迁移备份 | 按新的迁移框架实现（第 8 节） | 保留最近一份已知良好的副本，并设空间上限 |
| UI 偏好、日志、AI 历史 | 明确保留期限 | 不随对外项目包导出 |

### 6.2 存储耐久性

- **persist**：在用户第一次导入或保存时，伴随用户手势请求。
- **诊断面板**：显示 `estimate()` 和 persist 结果。
- **Safari 风险提示**，按收窄后的措辞：“按 WebKit 2020 年的 ITP 说明，在 Safari 中使用满 7 天、期间没有与本站交互的，可能删除 IndexedDB 等脚本可写存储；添加到主屏幕的 Web App 单独计数。当前版本未实测。”
- **QuotaExceededError**：统一处理，不自动删除原件。
- **站点外备份**：支持 FSA 的浏览器用备份文件夹轮换写入 JYB；不支持的浏览器提醒用户下载。
- **origin 固定**：域名、端口、协议都不要变。

### 6.3 代码边界

- **分层原则不变**：UI → service → db。
- **基线重置时一并收拢**：
  - 目录表清单目前有 4 份副本，合并成一处。
  - 删除项目只保留一个入口。
  - `pages/components` 里直接 import db 或 services 的地方（分别有 51 处和 28 处），按领域逐步收拢，不要求一次清完。

## 7. 项目包、整库备份与互操作

### 7.1 出口（D1，去掉旧格式读取）

| 格式 | 范围 | 媒体 | 用途 |
| --- | --- | --- | --- |
| JYM | 单项目，可编辑 | 默认包含受管媒体；不含时 manifest 写 `media: excluded` | 交付、迁移项目 |
| JYT | 单项目，轻量 | **不含媒体**，类似 EAF；每行声明 `bytes: omitted`；界面标“不含音频” | 交换标注和数据 |
| JYB | 整库备份 | 必须写明是否含音频 | 灾备 |
| 交换格式 | EAF、TextGrid、TRS、FLEx、Toolbox、LIFT | — | 附带“未能表示的字段”报告 |

- 新格式的 `formatVersion` 从 1 开始，使用新的 mimetype。
- 现有的 JYM/JYT 导出与导入代码，在第 3 批直接替换掉。

### 7.2 manifest

结构是文件条目数组，字段如下：

```
formatVersion, appVersion, created, kind: project|library,
media: included|excluded, digestAlgorithm: sha256,
projects[]: { id, restoredFrom?, documents[]: { documentId, layers[], sources[] } },
files[]: { path, sha256, size, role, entityType?, entityId?, bytes?: included|omitted, mediaStatus?, derivedFrom? },
dependencies[], excluded[]: { kind, count, reason }
```

- **路径**：由 ID 生成；按 OCFL 规则做安全校验；拒绝重复条目。
- **sha256**：只用来校验完整性、提示重复，不作为身份。
- **不进包的内容**：clientId、协作绑定、凭据。

### 7.3 依赖范围

项目包包含：
- 项目内容；
- 项目拥有的**全部**目录行。

因为归属在写入时强制，所以不存在无主行，也就不需要导出前先认领。

### 7.4 入站流程

1. 先校验清单、版本、路径、上限、哈希和引用，全部通过后再写入。
2. JYM/JYT 默认作为新项目恢复：重映射引用，记录 `restoredFrom`。
3. 覆盖当前项目：只对从未协作过的本地项目提供（D5，判定方式见 D6）。流程是：二次确认 → 自动生成覆盖前快照 → 写入。快照失败就中止。
4. JYB 的两种恢复模式：
   - **逐项目导入**（默认）。
   - **整库替换**：仅在本地库为空，或者所有项目都从未协作过时提供（D7）；需要二次确认，并先做整库快照。
5. 失败项和跳过项都要列清单。
6. 小包用单个事务；大包先暂存，最后一次性提交。
7. 遇到未知版本或旧版整库包，一律拒绝并给出说明。
8. 导出和导入的容量上限保持对称，同步压缩的上限需要实测。

## 8. Schema 基线与迁移安全

### 8.1 基线重置（推荐）

**做法**
1. 新建主库，名称建议用 `jieyu`，或 `jieyudb_v3` 以示区分（P1 待定）。
   - 只声明一个 `version(1)`，内容是按第 4 节整理好的完整 schema：
     - `source_records` 表；
     - 媒体状态字段，必填；
     - `documentId`；
     - 目录 `textId`，必填；
     - 唯一索引按需添加。
   - 删除旧主库的 `version(1..54)` 声明（`engine.ts:464-1505`）。
2. 删除迁移代码和测试：
   - 删除 `src/db/migrations/` 下的迁移文件，以及 `dbUnificationMigrationReplay`、`segmentationV2Migration`、`dbUnificationIdempotency` 等专为迁移写的测试。
   - `timelineUnitMapping.ts` 被运行时代码 `LayerSegmentGraphService.ts:17` 引用，要**移到 services 或 utils 下，不能删**。
   - 删除前逐个文件确认没有运行时引用。
3. 删除兼容分支：
   - `io.ts` 中 `orthography_transforms` 的别名映射和对 `audioDataUrl` 的回灌；
   - `mediaItemTimelineKind` 的启发式推断；
   - `claimUnscopedCatalog`；
   - 其他打着 `legacy` 标记的分支。全仓 73 个源文件提到 legacy，需要**逐个**判断它是兼容代码，还是只是命名里带了这个词。
4. 删除旧的升级前备份实现：`preMigrationBackup.ts` 和 `engine.ts` 里 `_createDb` 中依赖错误版本比较的迁移分支（`:1618-1697`，以及 `:1815` 起的抽查）。第 4 批会按 8.2 重写。
5. 其他 IndexedDB 库的 schema 历史，也按同样的方式整理成各自的 `version(1)`。
6. 快照格式 `SNAPSHOT_SCHEMA_VERSION` 和协作快照格式的版本号，都从新值重新开始。
7. 云端（可选，P3）：把 `supabase/sql/001-004` 合并成一个基线脚本，清空开发环境的云端数据。

**需要的条件**
- 所有开发和测试设备都要清一次本 origin 的站点数据（8 个 IndexedDB 库，加上 localStorage）。
- 也可以由应用在启动时检测到旧库名后提示，并在用户确认后删除，见 P1。
- 用户自己设备上的测试项目会丢失。需要保留的，在重置之前用现有的 JSON 导出留一份参考；**这份导出不会被新版本导入**。

**风险**
- **漏删**：遗漏的运行时依赖会导致构建或运行失败。用 typecheck、knip 和全量 vitest 兜底。
- **测试**：部分现有测试断言的就是迁移后的行为，需要逐个改写。
- **一次性操作**：基线重置只能在冻结点之前做。冻结点之后，就只能走 8.2 的迁移。
- **实测**：评估删除量时没有逐行确认，第 2A 批开工时要重新清点。

### 8.2 迁移框架（冻结点之后适用；第 4 批完成，发布阻断）

**分级（D2）**
- 每个版本都要声明 `additive` 或 `rewriting`；没有声明的，按 rewriting 处理。
- 分级按 `(from, to]` 区间整体判断。
- 以下都算 rewriting：新增唯一索引、修改主键、删除表。
- rewriting：只有升级前快照成功，才允许执行。快照失败就阻止升级，停在旧版本，并提供恢复导出。
- additive：快照失败时可以继续，但要给出可见的警告。

**版本检测（取代 N12）**
- 统一使用 Dexie 版本号，即原生版本 / 10。
- 同时用一个合成的 v1→v2 夹具测试来锁定这一点，避免再次出现单位错误。

**恢复导出**
- 不经过 `getDb()`：用原生 IndexedDB、不指定版本打开数据库，按 store 只读读取，生成含字节的 ZIP。
- 导出结果可以用 JYB 的逐项目模式导入。

**快照**
- 写到隔离的库里；只保留最近一份已知良好的副本，并设空间上限，事先做配额预检。
- 恢复时要重建索引和主键。

**其他**
- 数据版本比代码版本高时，提示用户更新应用。
- upgrader 里不调用 WebCrypto，也不调用 fetch。

### 8.3 其他

- **恢复快照**：按当前项目读取；超过上限时清理或标为过期，并在界面上显示。
- **ADR-0008**：需要修改“绿场”前提，改为“冻结点之前绿场，冻结点之后受迁移安全约束”。

## 9. 协作删除安全（第 2C 批）

与修订三相同：
- **两种删除**：“仅从本机移除”和“删除云端项目”（只有 owner 可以执行）。
- **清理任务**：持久化、可以重试。
- **项目级墓碑**：长期保留，冲突时删除优先（delete-wins）。
- **服务端**：用 RLS 或触发器拒绝对已删除项目的写入。
- **待发操作**：删除时标为 `cancelled_by_delete`。
- **clientId**：每个安装实例生成一次，不随项目包复制。
- **协作 restore**：遵守 4.2-7；prune 和写入放在同一个事务里，或者先暂存再提交。

D9 之后的简化：
- 不需要处理“旧客户端、旧队列格式”。
- 协作状态库可以随基线重置一并清空。
- 有了稳定的 clientId 和持久的协作绑定记录，D6 中“判定不了”的情况基本只会在数据损坏时出现。
