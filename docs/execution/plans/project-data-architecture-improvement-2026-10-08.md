# 项目、资料与持久化架构改进方案

## 1. 目标与状态

解语是本地优先的田野语言资料研究工作台，需要长期保存录音、解释标注来源、可靠协作并与外部工具交换资料。本方案将项目组织、文件身份、领域写入、持久化、归档和代码治理作为同一条数据生命周期处理。

本文件为待实施方案，综合[代码调查](../audits/project-file-architecture-review-2026-10-08.md)及领域调研；没有修改生产数据库。当前代码事实与目标设计分别描述。实施需逐批记录验证证据，不能将任务勾选或文档检查代替真实数据验收。

成功标准：同名资料不会误覆盖；关联在改名和重载后稳定；删除录音保留已有时间轴；一个项目可携带必要依赖迁出并完整恢复；失败不会误报成功；代码边界能支持上述行为。

范围外：更换 Dexie、微服务、monorepo、全仓目录搬迁、引入 CRDT、通用文件管理器、一次性实现完整档案馆平台。

## 2. 已确认现状与问题

| 当前事实 | 主要缺口 |
| --- | --- |
| 项目以 texts/textId 表示，录音在 media_items | 项目、资料组、标注文档的概念边界需明确 |
| 来源保存在 metadata.sourceFiles，内容在 layer_units/contents 等表 | 来源记录与编辑内容尚无完整作用域关系 |
| 来源 ID 由格式和小写文件名组成 | 同名不同内容覆盖来源记录 |
| 可用文件名回退关联录音 | 多个同名录音会产生歧义 |
| 来源登记与改名读取项目后整行 put | 未以事务保护读改写，存在丢更新窗口 |
| JYM/JYT 调用整库 JSON 导出，无 textId 参数，未额外打包媒体 | 项目范围与完整可携带归档不成立，需要核对并修正产品契约 |
| JSON 省略媒体/词典附件 Blob；快照格式仅接受当前版本 | 原件保存及版本兼容需建立长期承诺 |
| 恢复快照先整库导出再筛选，超过 8 MiB 跳过 | 成本受全库影响，失败/跳过状态不充分可见 |
| 迁移前备份失败后仍继续升级 | 长期真实数据场景需要风险分级策略 |
| 多个存储库已有不同程度的清理；启动请求 persist | 缺少统一的责任、配额、恢复与清理清单 |
| 架构地图同页存在 v34/v53/v54 等矛盾 | 当前状态文档不能完全作为事实依据 |

同名、并发和归档问题有静态实现依据，尚未全部经真实 UI 重现；跨库删除残留、性能上限与云端运行行为作为待验证风险，不宣称已发生数据损坏。

## 3. 成熟方案依据与取舍

| 来源 | 借鉴内容 | 采用边界 |
| --- | --- | --- |
| [ELAR / lameta](https://blogs.soas.ac.uk/elar/2020/04/30/introducing-lameta/) | Session 对应资料 bundle，参与者独立管理 | 引入资料组语义；不复制全部档案元数据表单 |
| [ELAN 文档模型](https://www.mpi.nl/tools/elan/docs/manual/Ch_ELAN_documents.html) | 媒体和标注分离，层与时间对齐关系显式化 | 延续现有标注真源与删音留轴 |
| [Zotero 集合](https://www.zotero.org/support/collections_and_tags)、[附件](https://www.zotero.org/support/attaching_files) | 分类与删除分开，受管文件与外部链接分开 | 展示树不决定实体所有权 |
| [Joplin 架构](https://joplinapp.org/help/dev/spec/architecture/)与[同步](https://joplinapp.org/help/dev/spec/sync/) | 服务/模型分层，同步独立处理状态 | 复用现有 service、db 和协作入口 |
| [Audacity 项目](https://manual.audacityteam.org/man/audacity_projects.html) | 可编辑项目保存与媒体导出不同 | 区分项目包、整库备份、交换格式 |
| [RO-Crate](https://www.researchobject.org/ro-crate/specification/1.1/introduction.html) | 文件、人物、软件及研究上下文的可解释描述 | 首版采纳清单与关系原则；未做合规验证不标称 RO-Crate 兼容 |
| [BagIt RFC 8493](https://datatracker.ietf.org/doc/html/rfc8493) | 清单与校验和 | 采用完整性校验；完整 BagIt 出口后置 |
| [MDN 存储配额](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) | origin 配额、persist、estimate | 分库不视为配额隔离；站点外归档承担备份责任 |

结论：适配成熟的数据语义，复用 Dexie、fflate 和既有领域模块；首批不新增依赖。后续若需要流式归档库，单独比较维护状况、体积、许可、浏览器兼容与取消/错误恢复能力。保留同步压缩只能在明确的受支持体量内使用，不能未经测量宣称支持大规模录音。

## 4. 目标领域模型

### 4.1 概念与关系

| 对象 | 身份与责任 | 推荐关系 |
| --- | --- | --- |
| Project 项目 | 研究范围、元信息、访问设置；沿用 textId | 拥有资料组与项目独占数据 |
| MaterialGroup 资料组 | 一次采录事件或一组共同处理的材料 | 关联零到多份媒体和标注文档；允许纯文字 |
| MediaResource 媒体 | 独立 ID、原名、显示名、格式、大小、哈希、可用状态 | 原始/派生关系显式记录；可保留无字节的时间轴宿主 |
| AnnotationDocument 标注文档 | 独立 ID、语言/层范围、关联时间轴和来源 | 内容仍在现有规范化单元图中，禁止再复制一份转写正文 |
| SourceRecord 导入来源 | 原始文件身份、原名、可选保存字节、导入时间及处理信息 | 导入活动连接来源、文档和产出层/单元 |
| SharedAsset 共享资产 | 说话人、词条、正字法、模板等 | 通过稳定 ID 引用；明确共享或项目所有 |

这是逻辑模型，不要求六张新表。资料组和标注文档只有在其独立查询、作用域和生命周期验收确定后才落表；现有 texts 不立即改名。新概念的用户文案与内部类型名可以不同。

### 4.2 最小落地和演进门槛

1. 首批继续保留 metadata.sourceFiles，独立生成新 ID，保留旧 ID；新增 originalName/displayName 时保留旧 name 读取兼容。
2. 所有读改写进入现有 projectFileOps 事务边界；项目不存在时返回明确结果，不能无声忽略后报告成功。
3. mediaId 关联校验项目归属与实体存在；逻辑占位媒体是合法宿主。无 ID 时唯一文件名候选可提示匹配，多候选进入未关联状态。
4. 内容指纹用于完整性和重复候选，不把同字节必然视为同一研究对象。重新导入与新增来源是不同操作。
5. 多文稿来源映射成立后引入 AnnotationDocument；按实际作用域引用层或单元，不能凭文件名回填归属。
6. 资料组首版以可选组织信息逐步接入，旧项目允许未分组；只有上下文明确才自动分组。无法恢复的历史来源标记 unknown，不制造原件或出处。

### 4.3 元信息

项目：标题、研究说明、语言与工作语言、负责人/贡献者、默认访问范围。资料组：采录时间、地点（可降低公开精度）、体裁、参与者及角色、说明。媒体：原名、显示名、媒体格式/时长/采样信息、哈希、原件/派生关系。标注文档：语言、层体系、创建/修改者、审核状态、来源。

必填仅稳定 ID 和有效归属；研究元数据逐步补充，允许未知。真实业务字段进入 typed schema 和校验；扩展元数据保留可扩展容器。参与者授权、敏感身份与公开描述分开保存和导出，不假定“可归档”就等于“可公开”。

## 5. 操作与界面契约

| 操作 | 必须保持的行为 |
| --- | --- |
| 首次导入 | 验证后写内容与可追踪来源；声明成功范围，保留失败恢复信息 |
| 再次导入 | 区分新建、更新既有文档；相同名称不能静默覆盖；覆盖预览影响范围 |
| 改名 | 只改显示信息，不改变 ID、引用或磁盘原件 |
| 挂接/替换媒体 | 保留身份或明确创建派生资源；校验时长/时间轴兼容，必要时预览，不能自动缩放标注 |
| 移除关联 | 不删除原件和编辑内容 |
| 删除录音字节 | 延续 deleteAudioPreserveTimeline；重载后文本和时间码不变，标明缺音 |
| 删除标注文档 | 只有有明确独占范围时才删除内容；共享层/单元需明确处理，不按源文件名推断 |
| 删除项目 | 清理独占数据；共享对象保留；同步队列需终止或记删除状态，避免离线操作复活项目 |
| AI/批处理 | 记录输入来源、工具/必要版本、输出和审核状态；采纳通过既有写入门，不另建内容真源 |

保留现有左侧面板切换、折叠侧栏和工作区骨架。关联文稿继续显示在录音题名下；没有录音的文稿保持可访问；多媒体关联不靠重复复制文档实现。后续资料组 UI 以真实多文件场景为依据。新增文案走 dictKeys/字典，颜色走语义 token。

## 6. 持久化与代码组织

### 6.1 存储分类

| 数据 | 保存/失败策略 | 备份与清理 |
| --- | --- | --- |
| 项目、内容和关系 | 主 Dexie；事务、边界校验、写后读回；失败不得报成功 | 纳入项目包/整库备份 |
| 原始媒体与附件 | 首版复用 Blob 存储；显式标记受管、外链或缺失 | 完整包包含受管字节；外链列明且不能冒充完整离线包 |
| 波形、向量、声学/统计派生数据 | 可重建，按已有策略限制容量 | 默认不进入长期项目包；只清理已确认可再生成内容 |
| 协作出站队列 | 未确认送达前可靠保留，展示 pending/failed | 不作为普通缓存清除；验证重启和删除后的行为 |
| 恢复/迁移快照 | 显式 success/skipped/failed 及最近有效时间 | 按数量/空间/版本设保留策略，保护当前恢复点 |
| UI 偏好与会话状态 | 沿用 localStorage/sessionStorage | 不进入研究项目核心归档 |
| 行为日志与 AI 历史 | 明确保留期限、是否为研究证据 | 默认不随对外项目包泄出；用户可选择需保留记录 |

保存提示区分编辑已持久化、同步是否完成、备份是否包含媒体。存储诊断显示估算用量和持久化授权结果；不把 persist 拒绝阻断普通启动。空间不足时提示清理可重建缓存或导出，不自动删除用户原件。

### 6.2 代码边界

UI/controller 负责交互；service 负责完整领域操作；db 负责事务、schema、迁移和校验；worker 承载经测量需移出的重计算。复用现有 app 门面，逐步减少经门面暴露的裸数据库业务操作。类型文件拆分以实际领域改动为切入点，保留公共导出兼容面，不修改历史迁移语义以追求行数下降。

## 7. 项目包、整库备份与互操作

三种出口分别命名和验收：当前项目可编辑包、整库备份、EAF/TextGrid/LIFT 等交换格式。交换格式应报告不能表示的字段和层约束，不承诺所有格式无损。

项目包建议延续现有 ZIP 容器能力，增加显式版本化 manifest：项目 ID、应用/格式版本、生成时间、包含范围、依赖清单、媒体状态、文件相对路径、大小和 SHA-256。包内路径使用稳定 ID，原名作为元数据，拒绝路径穿越和重复条目。

可采用 `data/`、`media/`、`sources/`、`metadata/`、`interchange/` 的归档目录；这些目录不要求映射为运行时目录。原始导入文件未保存时诚实标记；不能用当前导出文件冒充原始来源。

依赖闭包包括项目内容和其必需的说话人、词典链接目标、正字法/模板等；共享对象按实际引用选择。协作快照排除策略不可直接充当完整项目包策略。其他项目的私有内容、凭据、协作身份令牌默认排除。

入站先验证清单、版本、路径、大小/数量上限、哈希与引用，再进入写入。小包可用单事务；大包需暂存与最终提交边界，不能出现半导入项目。支持取消和清理仅本次暂存。重复导入区分更新同一项目与导入为副本；副本需完整重映射引用，不能只改项目 ID。

当前 JYM/JYT 旧包继续走旧读取路径并告知能力限制；新包使用新的显式归档版本。导出与导入容量上限必须对称。跨版本兼容窗口在归档 ADR 中按已有用户数据和发布版本确定；未知新版本拒绝写入并给出升级说明。

## 8. 迁移与恢复策略

- 正式升级不再以变更数据库名称作为默认数据迁移手段；现有 jieyudb_v2 保持。
- schema 版本在实施时基于最新版本递增；不在本计划预占 55，避免其他任务冲突。
- 旧来源 ID 保留；新增字段允许缺失并确定性回填；同名已覆盖的历史来源无法凭空恢复。
- 破坏性迁移要求可验证恢复点；备份失败时停止破坏性升级并提供重试/导出路径。兼容性新增迁移按风险单独制定策略，不让所有启动都依赖成功复制整个媒体库。
- 回退不能只回退前端代码；schema 已变化时用验证过的迁移前数据和兼容应用版本，禁止低版本直接改写新 schema。
- 恢复快照按需要的集合/项目范围读取，超限或失败返回明确结果；beforeunload 异步写仅作补充，不作为唯一保障。
- 大体量备份、空间不足、多标签占用、强制关闭与失败恢复必须在隔离浏览器配置中演练。

## 9. 实施批次与具体落位

| 批次 | 主要落位与类别 | 交付及退出条件 |
| --- | --- | --- |
| P0 基线与复现 | projectSourceFiles/projectFileOps/JymService 的测试；现状地图 | 建立双项目、多同名文件、无音文稿夹具；重现并记录范围/身份问题，更新错误文档 |
| P1 身份与关联 | utils/projectSourceFiles.ts、services/projectFileOps.ts；derived/actions | 稳定来源 ID、事务更新、显式关联校验；改名/并发/重载不丢数据 |
| P2 来源与文档 | importHandlers、领域写服务、db types/schema/migrations；actions/state | 明确导入活动及文档作用域；内容与来源有可恢复一致性边界；纯文字、多文稿场景通过 |
| P3 项目归档 | JymService、db/io、专用项目依赖选择模块、导入导出 UI；actions/derived | 单项目隔离、媒体/依赖完整、哈希和空环境恢复通过；包大小在支持范围内 |
| P4 存储与恢复 | SnapshotService、preMigrationBackup、恢复 hooks、设置诊断；effect/state | 配额/超限/失败可见；按范围读取；迁移及恢复演练通过 |
| P5 资料组织与协作 | project 组件、workbench controller、资料组领域服务、协作协议；routing/actions | 可选资料组、多资源关联；删除与离线队列一致，保留现有 UI 骨架 |
| P6 收口发布 | 架构地图、相关热点、release gates | 边界守卫、运行证据和支持范围文档齐全；清理已结束 flag |

依赖：P0 → P1 → P2 → P3；P4 可在 P1 后独立推进，破坏性迁移前必须完成相应恢复保障；P5 依赖 P2 的领域作用域；P6 按批持续进行。不以全部批次完成作为发布单个安全修复的前提。

每批 implementation 前建立独立 SDD 三件套；P2/P3/P4/P5 涉 schema、协议或不可逆决定时同步 ADR。大幅 UI/高风险新能力遵守默认关闭 flag 和自用一周规则；数据正确性修复无需保留旧错误分支。schema 兼容不依赖 UI flag。

## 10. 验收矩阵与证据

| 场景 | 业务断言 |
| --- | --- |
| 同名不同内容文稿 | 来源可区分；原内容不会无提示被替换 |
| 同名音频/失效 ID | 无歧义才关联；错误项目/不存在媒体拒绝或明确未关联 |
| 改名与重复导入 | 身份、显示名、原名和更新策略一致 |
| 并发来源登记/元数据编辑 | 两份更新重查都存在 |
| 导入中途失败 | 不报完整成功；没有不可解释的孤立内容；可重试且不重复 |
| 删除录音再挂接 | 句段、时间码与标注保持，媒体状态准确 |
| 删除项目与共享资产 | 独占数据清理、共享对象保留、队列不复活已删内容 |
| 项目 A 归档 | 解包无项目 B 私有数据；空环境导入后层、引用和媒体正确 |
| 大包/损坏包/取消 | 输入完整验证，失败无半成品；导出的受支持包能够读回 |
| 旧库与旧包 | 指定支持版本可迁移；未知版本零写入；旧 ID 引用不变 |
| 配额/快照超限 | 明确失败/跳过；最近有效恢复点可辨识，无误报成功 |
| Chromium/WebKit/Firefox | 按浏览器支持策略验证实际 IndexedDB/Blob 路径 |

自动验证：typecheck、触及域的 Vitest；UI/装配改动加 Chromium E2E，持久化敏感路径扩支持浏览器；结构改动跑 architecture guard；文档跑 docs-governance/plans-frontmatter。真实 Supabase 验收与 mock 契约结果分开记录。
