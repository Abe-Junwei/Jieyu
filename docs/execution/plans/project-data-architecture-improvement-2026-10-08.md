## 1. 目标与状态

解语是本地优先的田野语言资料研究工作台，要长期保存录音、说明标注来源、可靠协作，并与外部工具交换资料。

**依据**
- 审查草稿（F1–F8）。
- 2026-10-08 对 `origin/main@85ff9f82` 的代码调查（功能分支的数据层与它相同）。
- 同类产品调研。
- 对修订二、修订四的外部评审。
- D9 约束。

**本文的写法**
- 当前代码的事实和目标设计分开写。
- 标“已复现”的问题，都是在 fake-indexeddb 中复现的。

**D9 带来的两个变化**

1. **现在可以直接改 schema、ID 和格式，不需要迁移，也不需要兼容层。**
2. **数据冻结点之前和之后，规则不同。**
   - 冻结点（**D14**，取代 D13）：**首次需要保留有价值的数据，或首次交给非开发者使用，以先到者为准。**
   - “有价值的数据”指任何人（包括开发者自己）准备长期保留、丢失后需要重做的数据，例如真实标注、整理过的语料、田野录音。田野采录只是其中一种。
   - 冻结要明确宣布：在 ADR-0008 和修改记录里写下冻结日期和对应的基线版本，不靠事后推断。
   - 冻结点之前：可以随时重置基线。
   - 冻结点之后：基线冻结，任何 schema 变化都必须走第 8 节的迁移安全机制。
   - 凡写着“发布阻断”的事项，都必须在冻结点之前完成。

**冻结之前的使用约束（D14 带来的）**
- 在冻结之前，不要把需要保留的数据放进应用。确实需要保留时，就应该先宣布冻结，而宣布冻结的前提是发布阻断事项都已完成（10.0）。
- 冻结之前的构建版本在界面上常驻提示“开发期版本：数据可能在升级时被重置，请勿存放需要保留的资料”（2A 实现，T56）。

**“没有历史数据”不等于“没有并发的旧东西”。** 即使没有旧数据，下面这些情况仍然存在，修订五都按“必须处理”对待：
- 同一浏览器里还开着运行旧代码的标签页；
- 协作者还在用 Service Worker 缓存的旧版本；
- 协议升级前后，客户端和服务器的版本不一致。

**成功标准**
- S1 同名资料不会被误覆盖。
- S2 改名、重载之后，关联关系不变。
- S3 删除录音后时间轴保留；恢复或导入不会抹掉本机的媒体字节和附件字节。
- S4 单个项目能连同依赖一起导出，并在空库中完整恢复。
- S5 失败或跳过不会被报告成成功。
- S6 已删除的项目不会复活；“仅从本机移除”不会影响其他协作者。
- S7 代码边界能支撑以上行为。
- S8 冻结点之后的每一次 schema 变化，都有恢复点和阻止策略。
- **S9（新增）每一个合入点都可以正常运行**：不存在“schema 已经改了，但写入方还没改”的中间状态。

**范围外**：更换 Dexie、微服务、monorepo、全仓目录搬迁、CRDT、通用文件管理器、完整的档案馆平台。

## 3. 成熟方案依据（压缩）

修订三第 3 节的依据仍然有效，这里只列出仍会用到的：

- **身份与名称分离**（OCFL、Logseq、Zotero）。
- **外部 ID 优先**：EAF 的 URN 用于文档级匹配；LIFT 的 guid 只用于词条级匹配。
- **Relink 与重新导入分开**（Lightroom、ELAN）。
- **出口分开并标明保真度，恢复默认生成新项目**（Logseq、FLEx）。
- **升级前留副本，只写副本**（Zotero、audacity-project-tools）。
- **墓碑长期保留、冲突时删除优先、稳定的 ClientId**（Joplin、Lexbox、Harmony）。
- **persist 伴随用户手势请求；Safari ITP 风险措辞收窄；站点外备份**（web.dev、WebKit 2020/2023）。
- **Dexie**：
  - 事务里不能等待非 IDB 的异步调用；
  - upgrader 一旦发布就冻结；
  - 不校验字段，只认主键和索引；
  - 有 DBCore 中间件和表 hook 两种拦截方式；
  - 已经打开的旧连接收到 `versionchange` 时应主动关闭。

结论：继续复用 Dexie 和 fflate，第 1、2 批不新增依赖。

## 4. 目标领域模型

### 4.1 概念与关系

| 对象 | 身份与职责 | 关系 |
| --- | --- | --- |
| Project 项目 | textId、元信息、默认访问级别、`defaultDocumentId` | 拥有资料组、标注文档、媒体、来源、项目目录 |
| MaterialGroup 资料组 | 一次采录事件 | 第 5 批落地；可以先预留可选的 `groupId` |
| MediaResource 媒体 | UUID；原名、显示名、格式、`contentSize`、`contentSha256`、时长；`role: primary/derived`；**必填** `timelineKind: acoustic/placeholder`、`byteLocation: managed/url/none`、`availability: available/missing` | `derivedFrom` 记录派生关系 |
| AnnotationDocument 标注文档 | **`documentId` 是全局唯一的 UUID**；`isDefault` 是一个属性，项目上同时保存 `defaultDocumentId` 引用；层归属于文档；文档引用来源 | 一开始每个项目只有一份默认文档；多文稿 UI 放到第 5 批 |
| SourceRecord 导入来源 | 独立的 `source_records` 表；UUID；`originalName`、`displayName`、`format`、`byteSize`、`sha256`、`externalDocId?`、`importedAt`、`importBatchId`、`storedBytes` | 取代 `texts.metadata.sourceFiles` |
| ProjectCatalog 项目目录 | 说话人、词条、正字法等；**必须有项目归属**（`textId`，结构规则对应 `projectId`） | 跨项目复用的方式是“从其他项目导入”（复制并重映射 ID） |
| SystemTemplate 系统模板（新） | 只存在于代码里，ID 带版本号，例如 `system.leipzig-structural.v1`；只读 | 项目可以引用它，也可以把它“复制到项目”（4.2-9） |

### 4.2 规则

1. **来源身份**：一律使用 UUID。
2. **重新导入的匹配顺序**：
   1. EAF 的 URN 相同：判定为“更新已有文档”，先预览。
   2. sha256 相同：提示“内容相同”。
   3. 仅文件名相同：作为新来源，显示名自动加序号区分。
   4. LIFT 只做词条级匹配（guid 优先，没有 guid 时用 id），导出时补写 guid。
3. **哈希在事务外先算好**，再在事务里登记，写入后读回校验。
4. **媒体关联**：校验 mediaId 存在、且属于本项目；只有唯一候选时才提示匹配。
5. **写入边界**：提供 `patchProjectMetadata` 一类的事务原语；禁止对 texts 先 remove 再 insert；项目不存在时返回明确结果。
6. **导入**：主体、来源登记、清理都放在同一次提交里。
7. **入站字节语义**（修订五重写；适用于所有导入、恢复和协作 restore）：
   - 每个媒体、附件、来源原件条目都必须显式声明 `bytes: included | omitted`；缺少声明就判为格式错误，拒绝导入。
   - `omitted` 只有两种合法结果：
     - 本机已有同一 ID：**保留本机字节**，同时保留与字节对应的 `byteLocation`、`availability`、`contentSha256`、`contentSize`。
     - 本机没有：写成 `none + missing`。
   - 如果某个策略无法保留本机字节，例如 replace 类操作已经删掉了行，就**中止整个操作**，数据库保持原样，并列出原因。**不存在“预览里写明会丢多少，然后继续”的选项。**
   - 删除字节只能通过单独的显式操作“删除录音字节”完成（第 5 节）。
   - replace 类操作删行之前，先读出需要保留的字节，放在同一个事务里处理。
8. **标注文档**：
   - `documentId` 全局唯一；项目通过 `defaultDocumentId` 指向默认文档。
   - 导入、恢复为新项目时，documentId 和其他 ID 一样重新映射。
   - manifest 包含 `documents[]`，见 7.2。
9. **目录归属与系统模板**：
   - 目录行必须带项目归属，由统一写入校验（4.4）强制；service 在没有项目时拒绝写入并给出明确错误。
   - 删除 `claimUnscopedCatalog` 以及各读路径上的调用，读操作不再产生任何写入。
   - 系统模板（修订五新增）：
     - **存放**：只放在代码里。删除 `ensureSystemLeipzigStructuralProfileSeeded`，数据库里不再有 `scope: 'system'` 的行。统一写入校验拒绝写入 `system.*` ID。
     - **查询**：列表 = 代码中的系统模板（只读，带“系统”标记）+ 本项目的行。
     - **引用**：项目可以直接引用系统模板 ID；解析时先查代码，再查项目行。
     - **修改**：先“复制到项目”，生成新 UUID，并记录 `derivedFromSystemId`，然后修改副本。
     - **导出**：不导出系统模板本身，只保留引用。导入时如果引用的系统 ID 在当前代码里不存在，列入“未解析引用”清单。
     - **版本**：冻结点之后，已发布的系统模板 ID 不再改动内容；要改就发布新 ID，例如 `.v2`。
   - 同时修订 ADR-0044 第 2 条。
   - 没有活动项目时（D11）：词库、语言目录等页面要求先选择项目，显示空状态和“选择项目”入口。
10. **Relink 与重新导入分开**：Relink 保持 MediaResource ID 不变。
11. **占位时间轴的替换范围**（修订五新增）：
    - 导入音频时，只替换**一条**占位时间轴：用户明确选中的那一条，或者与当前文档显式关联的那一条。
    - 有多个候选、又没有明确选择时，要求用户选择，不自动合并。
    - 其他占位行和声学行都不变。

### 4.3 元信息与访问

与修订三相同：
- 访问级别在 项目 → 资料组 → 文件 三层之间继承，下层可以覆盖上层；词表候选为 `open / registered / restricted / community-protocol`，外加 `embargoUntil`。
- 必填项只有 ID 和归属。
- 同意书、敏感身份、公开描述分开保存。

### 4.4 统一写入校验（修订五新增）

**问题**：Dexie 的 stores 字符串只声明主键和索引，不会拒绝缺字段的行。“schema 必填”必须由代码来保证，而现在有 87 处直接写 Dexie 的调用，都不经过校验。

**做法**
- 在主库上注册一个 DBCore 中间件（`db.use({ stack: 'dbcore', … })`），对每张表的 `add`、`put`、`bulkPut` 等写入请求，用这张表的 zod 校验器逐行检查。不合格就抛出带表名和字段名的错误，事务随之回滚。
- `update`、`modify` 在 DBCore 层的具体请求形态，以实测为准。必要时再加表的 `updating` hook，对合并后的完整对象做校验。
- 校验内容包括：
  - 必填字段，例如媒体的三个状态字段、目录归属；
  - 枚举值；
  - 禁止写入 `system.*` 模板 ID。
- 导入路径照常先整体预校验，中间件是第二道防线。
- 校验器只能是同步函数，因为在事务里不能等待其他异步调用。
- 性能：大批量 `bulkPut` 要测量校验耗时；测量之前不承诺具体指标。

**位置**：属于 2A 的基础设施。之后每个纵向切片在加字段时，同步更新对应的校验器。

| 挂接或替换媒体 | Relink 保持身份，或者显式创建派生资源；时长不一致时先预览 |

| 删除录音字节 | 唯一允许删除字节的操作；保留原名；状态变为 `acoustic + none + missing` |
| 仅从本机移除项目 | 只写本机的“已移除”记录，不传播到服务器；如果有未同步的修改，先提示“同步后移除”或“放弃修改”；用可重试的清理任务删除本地数据（9.1） |
| 删除云端项目 | 只有 owner 可以执行；服务器写全局墓碑，冲突时删除优先；所有客户端看到墓碑后执行本地清理（9.2） |
| 导出 JYM / JYT / JYB | 按 D1 执行（7.1） |
| 导入 .jym / .jyt | 默认恢复为新项目；遇到不认识的格式或版本，提示后拒绝 |
| 覆盖当前项目 | 只对从未协作过的本地项目提供（D5、D6）；需要二次确认，并自动做覆盖前快照 |
| 恢复 JYB | “逐项目导入”或“灾难恢复”（D7，见 7.5） |
| 从其他项目导入目录 | 复制并重映射 ID（D3） |
| 使用或修改系统模板 | 直接引用；要修改就先“复制到项目”（4.2-9） |
| 在没有活动项目时操作目录 | 不允许（D11） |

### 6.2 存储耐久性

- **persist**：在用户第一次导入或保存时，伴随用户手势请求。
- **诊断面板**：显示 `estimate()` 和 persist 结果。
- **Safari 风险提示**：“按 WebKit 2020 年的 ITP 说明，在 Safari 中使用满 7 天、期间没有与本站交互的，可能删除 IndexedDB 等脚本可写存储；添加到主屏幕的 Web App 单独计数。当前版本未实测。”
- **写入失败**：统一处理 QuotaExceededError、AbortError、事务中止和连接被关闭，不自动删除原件，并且如实报告失败。
- **站点外备份**：支持 FSA 的浏览器用备份文件夹轮换写入 JYB；不支持的浏览器提醒用户下载。
- **origin 固定**：域名、端口、协议都不要变。

- 目录表清单合并为一处，供写入校验、删除项目、导出、JYB 分类共同使用。

| --- | --- | --- | --- |

### 7.2 manifest：按条目类型分别规定契约（修订五重写）

修订四把 `bytes?` 写成 `files[]` 上的可选字段，这和“每条都必须声明”矛盾；而且被省略的媒体在包里没有文件，它的 sha256 和 size 也就没有含义。修订五把“包里的文件”和“数据实体”分开写：

```
formatVersion, appVersion, created, kind: project|library, digestAlgorithm: sha256,
media: included|excluded|partial,
projects[]: { id, restoredFrom?, defaultDocumentId,
              documents[]: { documentId, isDefault, layerIds[], sourceIds[] } },
entities[]: 见下表（每个媒体、附件、来源原件各一条）,
files[]: { path, sha256, size, role: data|media|attachment|source-original },
systemRefs[]: { id }          // 被引用的系统模板 ID
excluded[]: { kind, count, reason }
```

| 条目 | 必填字段 | `bytes` | sha256 / size 描述什么 |
| --- | --- | --- | --- |
| `files[]` 数据文件（`role: data`） | path、sha256、size | 不适用 | 包里这个文件本身 |
| `files[]` 字节文件（media、attachment、source-original） | path、sha256、size | 不适用 | 包里这个文件本身；必须被恰好一个实体引用 |
| `entities[]` 媒体 | type、id、`bytes`、`timelineKind`、`byteLocation`、`availability` | **必填** | `contentSha256` / `contentSize` 描述**原始内容**：已知时填写，`omitted` 时也照样填写，供 Relink 时校验；未知（例如 url 或从未有过字节）时不填 |
| `entities[]` 附件（lexeme_assets） | 同媒体 | **必填** | 同媒体 |
| `entities[]` 来源原件 | type、id、`bytes` | **必填** | 同上 |
| `entities[]` url 媒体 | 同媒体，外加 `url` | 必须是 `omitted` | 不填 |

**一致性规则**（导入前全部检查，任何一条不满足就整体拒绝）：
- `bytes: included` ⇒ 有 `fileRef` 指向 `files[]` 里的一条，并且这条的 sha256、size 等于实体的 `contentSha256`、`contentSize`。
- `bytes: omitted` ⇒ 没有 `fileRef`，包里也没有对应文件。
- `files[]` 里的每个字节文件都被恰好一个实体引用；没有被引用的“孤儿文件”判为格式错误。
- 两个实体的字节完全相同时，仍然是两个实体、两个文件条目（T37）。
- 路径由 ID 生成，按 OCFL 规则做安全校验，拒绝重复条目。
- sha256 只用来校验完整性、提示重复，不作为身份。
- 不进包的内容：clientId、协作绑定、本机移除记录、凭据、系统模板本身。

### 7.3 依赖范围

项目包包含项目内容，以及项目拥有的**全部**目录行。系统模板只以 `systemRefs[]` 的形式出现。

### 7.4 入站流程

1. 先校验清单、版本、路径、上限、哈希、引用和 7.2 的一致性规则，全部通过后再写入。
2. JYM/JYT 默认作为新项目恢复：所有 ID 重新映射（包括 documentId），记录 `restoredFrom`。
3. 覆盖当前项目：只对从未协作过的本地项目提供（D5、D6）。流程是：二次确认 → 自动生成覆盖前快照 → 写入。快照失败就中止。
4. JYB 按 7.5 处理。
5. 失败项和跳过项都要列清单。
6. 小包用单个事务；大包先暂存，最后一次性提交。暂存期间失败时，清理暂存数据，主库保持不变。
7. 遇到未知格式或版本，一律拒绝并说明原因。
8. 导出和导入的容量上限保持对称，同步压缩的上限需要实测。

### 7.5 JYB 的两种模式与数据分类（修订五新增）

**两种模式的语义**

| | 逐项目导入（默认） | 灾难恢复（整库还原） |
| --- | --- | --- |
| 语义 | **导入**：把包里选中的项目作为新项目加入 | **还原**：让本机回到备份时的状态 |
| ID | 全部重新生成，记录 `restoredFrom` | 保留原 ID |
| 对本机现有数据 | 不碰 | 全部替换 |
| 前提 | 无 | 仅在本地库为空，或者所有项目都从未协作过时提供（D7）；需要二次确认，并先做整库快照，快照失败就中止 |
| 协作状态 | 新项目是未协作的本地项目 | 不还原协作绑定；还原后所有项目都是未协作状态 |

**数据分类表**

| 类别 | 例子 | 进 JYB | 逐项目导入 | 灾难恢复 |
| --- | --- | --- | --- | --- |
| 项目内容 | 项目、文档、层、单元、来源记录 | 是 | 重映射后导入 | 原样还原 |
| 项目目录 | 说话人、词条、正字法、结构规则 | 是 | 随项目一起重映射导入 | 原样还原 |
| 媒体与附件字节 | 音频、词条附件 | 按 `media` 选项 | `included` 的写入；`omitted` 的标为缺失 | 同左 |
| 系统模板 | Leipzig 结构规则 | 否（只保留引用） | 按 ID 解析 | 按 ID 解析 |
| 项目级 AI 记忆与 AI 历史 | `jieyu-project-memory`；主库里属于项目的 AI 数据 | 是 | 可选，默认随项目导入 | 还原 |
| 用户偏好 | 界面、语言、AI 参数（不含凭据） | 是（单独的 `settings` 条目） | 不导入 | 询问后还原 |
| 凭据与会话 | API key、登录会话 | **否** | — | — |
| 协作状态 | clientId、协作绑定、出站队列、云端 revision、本机移除记录 | **否** | — | — |
| 派生数据 | 声学缓存、波形峰值、搜索索引、向量 | 否 | 重新生成 | 重新生成 |
| 恢复快照、迁移备份 | `jieyu_recovery`、迁移快照库 | 否 | — | — |
| 语音会话、行为日志 | `jieyu-voice-sessions`、`jieyu-user-behavior` | 否（隐私） | — | — |

分类表和 6.3 的“目录表清单”放在同一处代码里，新增表时必须同时登记分类，否则测试失败（T53）。

### 8.2 迁移框架（冻结点之后适用；第 4 批完成，发布阻断）

**分级（D2）**
- 每个版本都要声明 `additive` 或 `rewriting`；没有声明的，按 rewriting 处理。
- 分级按 `(from, to]` 区间整体判断。
- 新增唯一索引、修改主键、删除表，都算 rewriting。
- rewriting：只有升级前快照成功并通过验证，才允许执行；否则停在旧版本，并提供恢复导出。
- additive：快照失败时可以继续，但要给出可见的警告。

**版本检测**：统一使用 Dexie 版本号（原生版本 / 10），并用合成的 v1→v2 夹具测试锁定。

**多标签页协调**（修订五新增）
- 所有标签页都注册 `versionchange` 处理：关闭连接，并提示“应用已更新，请刷新”。
- 升级前先用 Web Locks 取得独占锁 `jieyu-db-upgrade`，再用 BroadcastChannel 通知其他标签页暂停写入、关闭连接。
- 收到 `blocked`，或者超时还有连接没有关闭（例如运行旧代码、没有处理逻辑的标签页），就**中止升级**，提示用户关闭其他标签页，不在不一致的状态下继续。
- 不支持 Web Locks 的浏览器，只依靠 `versionchange` 和 `blocked`。

**快照：两个槽位轮换**（修订五新增）
- 新快照写入空闲槽位。写完后重新打开，逐个 store 核对行数，并抽样读回字节核对 sha256。全部通过后，才标为“已验证”，然后删除上一份。
- **在新快照验证通过之前，上一份可用快照一直保留。**
- 配额预检按“两份同时存在”估算。
- 写入中途失败（QuotaExceededError、AbortError、事务中止、标签页关闭）时：删掉不完整的槽位，保留上一份，按 D2 处理。启动时如果发现没有标记“已验证”的槽位，视为失败的残留，予以清理。
- 恢复时重建索引和主键。

**原始恢复快照与 JYB 的区别**（修订五新增）
- **恢复导出**：不经过 `getDb()`，用原生 IndexedDB、不指定版本打开数据库，按 store 只读读取，生成“原始快照 ZIP”。manifest 写明 `kind: raw-idb`、库名、原生版本号、Dexie 版本号和各 store 的行数。它保存的是**旧 schema 的原样数据，不是 JYB**。
- 原始快照有两种用法：
  1. **转换器**：把快照写进一个临时库，版本号与快照相同；用当前代码里保留的 upgrader 把它升到当前版本；再导出成当前 JYB，交给 7.5 的流程导入。这一步依赖第 3 批的 JYB。
  2. **原版本还原**：在对应的旧版应用里，把快照原样写回。
- 转换失败时，原始快照保持不变，并提示用户保留文件。

**其他**
- 数据版本比代码版本高时，提示用户更新应用，不尝试打开。
- upgrader 里不调用 WebCrypto，也不调用 fetch。

### 8.3 其他

- **恢复快照**：按当前项目读取；超过上限时清理或标为过期，并在界面上显示。
- **ADR-0008**：修改“绿场”前提，改为“冻结点之前绿场，冻结点之后受迁移安全约束”。

## 9. 协作删除安全（第 2C 批）

### 9.1 仅从本机移除（本地状态，不传播）

- 在本机写一条“已移除”记录（`projectId`、`removedAt`），这条记录永远不发给服务器。
- 有未同步的出站修改时，先让用户选择：“同步后移除”或“放弃这些修改”。
- 通过持久化、可重试的清理任务删除本地数据。
- 同一账号重新登录、或者自动拉取时，跳过已移除的项目；在“已从本机移除的云端项目”列表里，可以手动重新下载。
- 其他协作者完全不受影响。

### 9.2 删除云端项目（全局墓碑）

- 只有 owner 可以执行。
- 服务器写项目墓碑（例如 `projects.deleted_at` 加墓碑表），长期保留，冲突时删除优先。
- RLS 或触发器拒绝对已删除项目的任何写入。
- 各客户端看到墓碑后，把出站队列标为 `cancelled_by_delete`，并执行本地清理任务。

### 9.3 旧标签页、旧客户端与协议版本

现在已经有 `protocol_version`、`app_min_version` 和客户端守卫，修订五在这个基础上补齐：
- **服务器端检查**：在 `project_changes` 写入、以及资产和快照写入时，用触发器或 RPC 检查 `protocol_version` 等于项目的版本、客户端版本不低于 `app_min_version`，不满足就拒绝。这样防线不再只靠客户端。
- **涉及语义的变化要提高版本**：例如引入墓碑语义时，提高 `app_min_version`，让不认识墓碑的旧客户端无法写入。
- **推送前重新评估**：客户端每次推送前重新读取项目行并评估守卫；被拒绝后进入只读状态，提示刷新。
- **同一浏览器的其他标签页**：本机移除、云端删除、协议升级都通过 BroadcastChannel 通知；标签页获得焦点时也会重新检查。
- **Service Worker**：发布新版本后提示刷新，不让旧版本长期驻留。

### 9.4 其他

- clientId：每个安装实例生成一次，不随项目包复制。
- 协作 restore 遵守 4.2-7；prune 和写入放在同一个事务里，或者先暂存再提交。
- D6 的判定函数放在本批提供，第 3 批会用到。
