# 1b-6 按层确信存储合同草案

## 背景与状态

用户已确认转写与翻译分别判断、空卡可主动标记、正文修改清除原判断。当前格式 35 把 `self_certainty` 放在共享 `units` 上，不能表达这些语义。本文是 1b-6 的存储实施提案，**尚未实施，也不改变当前格式**；仅按层保存及其生命周期已获产品语义确认。审定后另写 accepted ADR，实施合同转入该 ADR 后删除本草案，不占用 ADR 编号。仓库 ADR 门禁只接受 accepted/superseded，本草案不作为已接受决定。

## 拟采用的合同

1. **一个正文记录一个判断。** 在 `unit_texts` 增加可空 `self_certainty`，值仅为 `not_understood`、`uncertain`、`certain` 或 NULL。正文身份仍为 `(unit_id, layer_id, role)`；`role` 必须由 `resolveUnitTextContext` 从目标层 `content_type` 派生，写调用方不自选 role。转写层与翻译层分别对应自己的行，不在同一层增加另一套可见判断。
2. **去掉共享真值。** 格式切换时删除 `units.self_certainty`，所有读写、拆合与快照改用正文行；不保留“没有正文行就回退共享值”，不双写，不把人工确信写进机器 `confidence`。不新增按本机缓存的确信真值。
3. **空正文载体按需存在。** `body=''` 合法。首次在空卡添加层备注或设置非空确信时，在同一事务创建对应正文行；录音已有同类载体，不预建所有空卡。清空正文时清除该行确信，但保留备注、录音及其稳定正文 id。只要仍有层备注、录音或非空确信，不得删除载体行。清除最后一项后无内容无引用的空行才可清理。普通保存、显式清空、正文撤销/恢复、分析恢复及拆合必须采用相同条件；不能让“正文未变”提前返回跳过元数据写入。
4. **生命周期按层执行。** 正文实际改变清除本层确信，正文未改变不清除；撤销恢复正文和原判断。拆分只有非空正文侧继承，空侧不继承；合并在每个层的全部来源间计算，任一来源缺行或未标记则结果 NULL，否则取最不确定档。空正文可以由用户重新标记。明确删除句段时按原删除规则处理全部所属内容；清空文字不等于删除句段。
5. **开发格式拟升到 36。** 当前代码仍为 35；36 是本提案目标，不是已落地版本。若实施前已有其他获准格式变更占用 36，先修订本提案再实施，不复用版本号。参照 ADR-0140 §决定 2：不迁移、不自动复制旧共享值；新程序拒绝旧 `project.sqlite` 且不改字节，旧程序不能打开新库。旧格式项目不能通过新程序导出，也不接受把旧程序导出的旧版本 JYT 当成迁移入口；manifest 与载荷的 `userVersion` 均须匹配。旧数据保留给对应旧程序查看，本轮受控合成项目重建；不删除用户材料、不承诺通用迁移。
6. **整条消费者链同批切换。** ADR 可先审定；schema、版本/冻结记录及全部依赖消费者必须在一个可构建、可读回的格式切换 PR 中交付，禁止先合入会破坏旧消费者的 schema-only PR。关闭新 UI flag 也不能回到旧列读写。交换包的正文列与版本、保存/编辑回执摘要和撤销基准均覆盖本层确信，防止撤销覆盖后改值。

## 空卡备注与完整性合同

工作区空卡备注业务操作接收目标 `{ unitId, textLayerId }`（批量为明确目标集合），而不是要求调用方先拿到并不存在的 unitTextId。事务内由 resolveUnitTextContext 派生 role，校验稿件/层/视图，再复用或创建正文载体，最后用既有 `{ kind: 'unit_text', unitTextId }` 持久锚点创建备注。底层 ContentNoteAnchor 无需同时支持两种正文身份；不允许前端分两次创建载体再写备注。operationId、目标列表、正文定位、视图快照和备注内容均进入回执摘要，失败不留半批载体或备注。

units、analysisRestore、recordingClips 三条清理路径统一条件；应用路径和不变量测试保证 active unit_text 备注目标存在，清空保留稳定 id。明确删除句段可按既有合同处理所属备注，不使用无差别拒绝所有删除的规则。当前格式已存在的备注孤儿风险先按实施规划 §11 的 6r 处理；本提案不承诺恢复无法追溯层身份的旧孤儿，也不把缺陷归为尚未实施的新功能。

## 阶段语义与交换

6p 只拆分，保留两段相同非空才继承的旧确信规则。6c 切换按层最不确定/NULL 优先的已批准语义并新增两段专门断言（当前 unitMerge.test 无此类断言），6d 再推广 N 段。新规则是明确的业务变更，不是通过削弱旧测试完成重构。

projectExchange 导入保留原 id；SELECT * 会带出新列，仍须验证列值与引用。先在 readPackage 核对 manifest/载荷版本，再在 insertPayload 比对列形状；单稿导出必须核对正文、空载体、notes 与录音过滤范围，不测试并不存在的通用 id 重映射。

## 消费者与验证

逐项消费者和可执行测试列在[1b-6 规划 §8–9](./1b-6-转写批量编辑-实施规划-2026-11-25.md)。至少包括 `units`、`unitTextLayers`、`unitTextClear`、`textSave`、`analysisRestore`、`unitSplit`、`unitMerge`、`unitSpan` / `RemovedUnit`、`sessionEdit`、`editReceipts`、项目读模型、notes/录音载体（含 `recordingClips.detachRecording`）与 `projectExchange`。改列存在本身不算交付：必须从注册入口写入、重查、关闭重开读回，并验证同一 unit 的两层不同值、空卡载体、拆合、后改拒绝和同版本交换往返。

## 未选方案

- 保留 `units` 值作兜底：层内空值与共享值竞争，重新引入跨层污染。
- 每个空卡都预建正文：没有内容也制造身份和清理负担；改为元数据第一次写入时创建。
- 单独确信表：已有正文稳定身份足以承载，不增加一套与正文/备注/录音协调的生命周期。
- 给 35 库补列并迁移：与开发格式冻结和本轮不迁移范围冲突。

旧网页 `src/utils/unitSelfCertainty.ts` 文件头记录过把层字段回写宿主造成的串层事故；只把它作为不选共享值兜底/宿主写入的证据，不调用其 deprecated helper。
