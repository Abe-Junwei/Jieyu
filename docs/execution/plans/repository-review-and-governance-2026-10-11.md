# 整库代码审查与治理完整方案

本方案合并整库 review 计划与覆盖缺口，按当前代码进度安排审查和治理。方案已开始执行；开始执行不代表整库审查通过，也不代表已获发布批准。

## 1. 目标、依据与边界

目标是回答四个问题：当前哪些能力真实可用；哪些路径可能丢数据、越权或中断工作；现有测试能否发现这些问题；如何以最小改动修复并持续防止复发。

主要依据：

- [AGENTS.md](../../../AGENTS.md)、[AI_QUICKSTART.md](../../../AI_QUICKSTART.md)、[项目工程约束](../../../copilot-instructions.md)。
- [仓库现状与代码地图](../../architecture/仓库现状与代码地图.md)、[代码治理计划](../../architecture/code-governance-plan-2026-05-06.md)、[ReadyWorkspace 装配边界](../../architecture/ReadyWorkspace-数据域与壳层装配边界.md)。
- [项目、资料与持久化修订五](./project-data-architecture-improvement-2026-10-08.md)及其批次验证记录。
- [单人 AI 协作拍板决策](./单人AI协作改进计划-拍板决策-2026-05-11.md)、[桌面浏览器支持策略](../../architecture/桌面端浏览器支持策略.md)。
- 当前源码、package scripts、workflow 和定向测试；历史报告仅作回归线索。

本轮规划复用既有服务、测试与 L0/L1/L2 体系，不新增产品架构或依赖，不触发 SDD。后续修复若新增 controller/service、跨三个 controller、改变 ReadyWorkspace、schema 或 flag，按仓库规则补 Research 和 SDD 三件套。既有架构决策继续有效；本方案不重新定义产品能力或兼容范围。

审查与修复分批交付。审查范围包括全仓受版本控制的生产代码、测试、脚本、构建部署配置、数据资产及关键文档；依赖实现按漏洞、调用路径和信任边界定向追踪。业务语义不确定时登记待裁决事项，不把猜测写成缺陷。

## 3. 审查方法与覆盖台账

审查单位是可达行为链：**入口 → 校验/授权 → 状态变化 → 领域写入/外部副作用 → 事务/持久化 → 缓存/事件/审计 → 重载或重新查询 → UI/下游结果**。

每个受版本控制文件归入一个主域，并标记生产、测试、fixture、开发工具、迁移、生成资产或第三方复制代码。全文件清单必须有归属，但不把“登记过”称为“逐行审查过”。

覆盖记录至少包含：域 ID、入口与源码位置、读写表/跨库存储、默认 flag、关联调用方、检查深度、测试编号、证据链接、目标 SHA、状态和遗漏理由。

- **必须深入追踪**：所有可达删除/覆盖/批量写入/迁移、跨项目访问、外部内容解析、凭据出站、AI 写工具授权、云端访问控制、媒体字节生命周期。
- **普通路径**：按能力和状态覆盖读路径、UI 与纯函数；同族抽样要列出代表样本及未深查成员，不能推断整族无问题。
- **生成资产**：检查生成器、来源、校验和消费路径；不逐行 review 大型生成 JSON。保留生成可重复性与许可证证据。
- **低风险/休眠代码**：识别静态和动态入口、flag、反射注册、脚本/fixture 用途。仍有引用但结果没有影响下游，不代表代码有价值。

覆盖状态使用 `not-started / traced / verified / blocked / not-applicable`。blocked 和 not-applicable 都需理由；前者不计通过。深查清单之外的抽样比例和剩余风险必须可见。

## 5. 安全与数据生命周期的具体检查表

针对录音、转写、来源原件、说话人资料、词典、AI 对话/记忆、凭据、遥测、协作元数据逐项登记：采集入口、项目归属、存储位置、复制/缓存位置、出站目的、导出包含规则、删除方式与剩余副本。

攻击者模型至少包括：提供恶意归档或语料的人、恶意模型/检索内容、权限较低的协作者、被篡改的服务地址或扩展、可利用同源 XSS 的攻击者。普通网页没有任意文件系统权限；本机被完全攻陷的恢复保证不纳入本轮。

核对项目删除与“仅本机移除”的差异，检查所有 IndexedDB 库、localStorage、缓存、后台队列、导出文件和云端记录。代码能删除的范围与用户需要手工管理的下载/备份副本要说明。云端身份、成员移除、会话失效和协议版本限制必须由服务端强制，客户端隐藏按钮不能作为授权证据。

解析器检查长度/嵌套/条目数量/展开比/实际大小与声明一致性，避免为边界测试真实分配数 GiB。加密包核查随机数、密钥派生、认证覆盖、错误口令零写入及元信息泄露边界；复用既有实现和标准库，不在审查中另写密码方案。

夹具至少含：两个项目、重名媒体、两个占位轴、多文稿多语言、多层投影与细分、词条引用、来源原件与附件、缺失字节、未知引用、已协作标志、合成升级版本。真实录音仅用用户授权的去敏副本；测试不得清理正在使用的浏览器 profile。

S/M/L 是待 A0 校准的负载建议，不是产品上限承诺：S 为 1 项目/2 音频/100 单元；M 为 10 项目/累计 1 万单元并含既有 160 MiB 包场景；L 为单项目 10 万单元与临近实际导入策略上限的测试。大包先用声明边界/受控 Blob/抽样替代高内存分配，必要时才在可承载环境运行。记录 CPU、内存、浏览器、编解码器、音频时长/采样率和冷热缓存。

正确性红线立即适用：零非预期数据丢失、越权、密钥泄露。性能预算先复跑既有 baseline，再按代表性设备和真实需求确认；不凭空指定统一毫秒门槛。AI 质量单独报告人工 gold set 的正确性、拒答与误用，工具执行成功率不能替代领域正确率。

## 9. 发现格式、分级与证据标准

每个 finding 使用 `RV-001` 等稳定 ID，记录：域/场景 ID、基线 SHA、文件和精确行号、可达入口、前置条件与最小输入、实际/期望结果、完整破坏链、数据影响、现有检查遗漏原因、复现证据、严重度、置信度、最小修复位置、回归方式、责任人与当前状态。

严重度与证据强度分别记录：

| 级别 | 定义                                                         | 处置                                         |
| ---- | ------------------------------------------------------------ | -------------------------------------------- |
| P0   | 正在发生或普遍可触发的大范围不可恢复损坏、任意越权或凭据泄露 | 立即止损，阻断相关功能与发布，保存证据后修复 |
| P1   | 明确条件下丢数据/错误覆盖/跨项目访问/核心工作流不可用        | 阻断涉及该路径的发布和冻结验收，优先修复     |
| P2   | 可恢复功能错误、代表性负载性能退化、关键分支缺少有效验证     | 纳入明确批次与验收，按受影响用户和频次排序   |
| P3   | 非阻断维护/文档/重复代码问题，有具体成本依据                 | 随相关变更收敛，避免独立大重构               |

证据标识：`source-confirmed`（可达且逻辑足以证明）、`test-reproduced`、`runtime-reproduced`、`needs-evidence`。单纯“可能会”留在假设清单；不作为已证实 bug。缺少测试按真实风险定级，不能仅因为没有覆盖率就判 P1。

状态流转：候选 → 已确认 → 待修复 → 修复中 → 已修待复验 → 已关闭；也可转为非问题、重复、风险接受或环境阻塞。关闭必须有修复 SHA 和复验证据。每条风险接受注明接受人、原因、使用范围、替代措施、复查日期/触发条件；AI 不代用户接受数据丢失或发布风险。

测试记录至少包含命令、退出码、收集/通过/失败/跳过数、重试、环境、fixture 版本、SHA、时间及日志位置。保留首次失败；日志脱敏，不上传用户录音或凭据。所有结论可追溯到真实输出，不能复制旧通过数充当新证据。

## 10. 修复与持续治理原则

1. **根因修复**：先查共享实现和全部调用者，在公共边界修一次；业务层问题不靠 UI 提示遮盖。先建立能失败的最小业务复现，再修正。
2. **持久化**：在 service/transaction 层保证校验、归属和原子性。跨库和网络边界不能假设单事务；明确失败后的恢复状态。修后必须重新查询/重开验证。
3. **结构**：保留既有 pages/hooks/services 目录体系。编排层只接线，纯计算用纯函数，写入用 service，状态协调用 controller；避免机械薄 hook 和大文件平移。按频繁改动与行为耦合决定拆分。
4. **删除与复用**：静态搜索、动态注册、flag、脚本和构建输出共同证明无用后才删除。优先使用已有模块与原生能力；不把“名字不同”当作必须合并的理由。
5. **界面**：尊重左侧切换和折叠侧栏骨架，按真实数据/控件验收；颜色映射 token、文案走字典、遵守两层容器边框。不把本轮审查扩成未要求的产品重设计。
6. **测试可信度**：断言可见业务结果与读回内容；收紧 pageerror filter/skip/allowlist 要有对应原因和用例。flaky 测试记录根因及修复任务，不靠长期增加重试过门禁。
7. **发布**：高风险或明显 UI 变化按现有 flag 流程。回滚需同时评估包格式/DB/服务端协议；前端退版不等于数据可回退。不可逆数据变更先证明恢复路径。
8. **提交**：一个可评审变更解决一个根因或紧密相关链路，说明为何、验证证据及未测范围。修复后按领域跑 typecheck、定向测试、必要 E2E/架构守卫；不混入本地无关导出文件。
9. **文档**：事实更新到 architecture，永久决策按 ADR，过程与发现进 audits/governance。审查只映射既有计划状态，确认后再收口；历史“未实施”和“已完成”均不能替代当前证据。

持续治理复用现有节奏：日常按改动跑 L0；合并用既有 L1；跨浏览器和重型 suite 留在 nightly/专项；发布用相关 L2。每次真实故障补一个有效回归/eval，季度或重大变更后复查高频热点、休眠 flag 和例外清单，不增加无产出的流程层。
