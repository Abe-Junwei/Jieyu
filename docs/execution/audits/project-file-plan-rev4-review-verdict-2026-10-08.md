# 对修订四外部评审的核查结论

**核查对象**：修订四原文，以及 `origin/main@85ff9f82` 的代码。功能分支的数据层代码与 `origin/main` 相同。本次只读，没有改动任何代码。

**核查结果的说明**
- 评审各点的编号按父代理转述的顺序排列，可能和原文编号不完全一致。
- 结论分三档：✅ 成立、◐ 部分成立、✗ 不成立。

## 1. T8 允许“在预览里写明会丢多少”就接受丢失（✅ 成立）

**证据**
- 修订四第 423 行的 T8 写的是：“replace-all 若做不到，预览里写明会丢失的数量”。这和 S3（恢复或导入不得抹掉本机字节），以及 4.2-7“入站缺字节永远不等于删除字节”自相矛盾。

**改动**
- 对 `omitted` 的处理只有两种合法结果：保留本机字节，或者中止整个操作。
- 删除字节只能由单独的显式操作完成。
- T8 增加一项检查：字节和元数据要一致，即 `byteLocation`、`availability`、`contentSha256`、`contentSize` 必须和实际存储的字节相符。

## 2. 墓碑的作用范围：“仅从本机移除”和“删除云端项目”（✅ 成立）

**证据**
- 修订四操作表第 167 行写：两种删除都要“写项目墓碑”。
- 第 9 节第 329 行的墓碑没有区分作用范围；修订三里原本有的 `scope: local|cloud` 在修订四中被压缩掉了。
- 如果“仅从本机移除”也写入会传播的墓碑，并且执行 delete-wins，就会删掉其他协作者的项目。

**另外两点也成立，但要更正一个前提**
- 即使没有历史数据，同一时间仍可能有旧标签页，或者运行旧版代码的协作者客户端。
- 协议版本字段其实已经有了，修订四没有写到：
  - 云端 `projects.protocol_version` 和 `app_min_version`（`001_collaboration_foundation.sql:71-73`），以及 `project_changes.protocol_version`（同文件 `:126`）。
  - 客户端守卫 `evaluateCollaborationProtocolGuard`（`collaborationProtocolGuard.ts:70-130`）：版本不匹配、或者应用版本低于 `app_min_version` 时，禁止云端写入。
- 但这层保护只在客户端：服务器 SQL 里没有任何触发器或策略会按 `protocol_version`、`app_min_version` 拒绝写入。旧标签页只有在重新读取项目行时才会被拦住；不带守卫的旧代码可以直接写入。

**改动**
- “本机移除状态”只记录在本地，不传播。
- “云端删除”使用服务器端的全局墓碑。
- 复用现有的 protocol_version / app_min_version：
  - 服务器在写入时检查这两个字段（触发器或 RPC），把防线从客户端挪到服务器。
  - 客户端每次推送前重新评估守卫；被拒绝后进入只读状态，并提示刷新。
  - 发生删除或协议升级时，通过 BroadcastChannel 通知同一浏览器里的其他标签页。

## 3. 2A 与 2B 之间存在半更新的中间状态（✅ 成立）

**证据**
- 修订四的 2A 把 `source_records` 表、必填的媒体状态字段、必填的 `textId` 都加进了基线 schema，但更新所有写入方的工作放在 2B。
- 2A 合入以后、2B 合入之前，要么写入因为缺字段而失败，要么写进不完整的行。代码里直接写 Dexie 的地方有 87 处（`dexie.*.put|bulkPut|add|update|modify`）。

**改动**
- 实施按“纵向切片”进行：每个切片包含模型、所有写入方、导出与读回、测试，每片单独合入后都必须可用。
- 批次表保留，只用于估算和排序。

## 4. T4 依赖 schema 来拒绝 NOT NULL，但 Dexie 不会强制执行（✅ 成立）

**证据**
- Dexie 的 stores 字符串只声明主键和索引，不校验字段。
- 现在的校验只在 `DexieCollectionAdapter.insert` 里（`adapter.ts:94-99`）和导入准备阶段执行。直接调用 `dexie.table.put/bulkPut/update` 的 87 处都不经过校验，例如认领逻辑里的 `table.update`。
- 仓库已经在用 Dexie 的表 hook（`engine.ts:1546-1548`，用于备份提醒），所以统一拦截在技术上可行。

**改动**
- 用 DBCore 中间件或者表 hook 统一校验所有写入，覆盖 `add/put/bulkPut/update/modify` 和导入路径。
- T4 改为分别测试：直接 `put`、`bulkPut`、`update` 和导入，四条路径都必须被拒绝。

## 5. 原生 IDB 恢复快照不等于当前格式的 JYB（✅ 成立）

**证据**
- 修订四 8.2 和 T41 说，恢复导出“可以用 JYB 的逐项目模式导入”。但恢复导出读出的是**旧版本 schema** 的原始 store，JYB 导入器只认当前 schema。中间必须有一个转换器（对快照运行对应版本的 upgrader），或者只能恢复到对应的旧版应用里。
- 修订四写“只保留最近一份”。如果新快照还没验证就覆盖了旧快照，一旦新快照损坏，就一份可用的都没有了。
- 升级可能被其他标签页阻塞（`versionchange`/`blocked`）。快照写入也可能中途失败，不只是配额预检不通过这一种情况。

**改动**
- 明确区分两种东西：“原始恢复快照”（旧 schema、原样保存）和“当前 JYB”。旧快照要转成 JYB，必须经过转换器。
- 新快照验证通过之前，保留上一份可用快照。
- 迁移前协调多个标签页：广播通知并等待其他标签页关闭连接，超时就中止。
- 快照写入失败、事务中止都按“快照失败”处理。

## 6. T22 把 `documentId = default` 当作键（✅ 成立）

**证据**
- 修订四 4.2-8 和 T22 让每个项目的第一份文档都使用 `default` 作为 documentId。如果文档表以 documentId 为主键，两个项目就会冲突；把 JYM 恢复成新项目时也会撞键。

**改动**
- documentId 一律使用全局唯一的 UUID。“默认文档”只是一个属性（`isDefault`）或项目上的引用（`defaultDocumentId`）。

## 7. “只合并 placeholder”的范围仍然太宽（✅ 成立）

**证据**
- `importAudio` 现在会把项目里**所有**占位行合并进同一个目标（`linguisticServiceMediaImport.ts:126-176`）。
- 修订四只是把“没有载荷”改成了“placeholder”。但在 D4 多文稿之后，一个项目可能有多条占位时间轴，导入一段音频仍然会把不同文档的时间轴并到一起。

**改动**
- 只替换用户明确选中、或者与当前文档显式关联的那**一条**占位时间轴。

## 8. JYB 两种恢复模式的语义不清，缺少分类表（✅ 成立）

**证据**
- 修订四 7.4 只写了“逐项目导入”和“整库替换”两种模式，没有说明各类数据如何处理：哪些进备份、哪些恢复、哪些排除、哪些重新生成。涉及的数据包括项目目录、AI 历史、偏好设置、协作状态、派生缓存、凭据等。

**改动**
- 新增分类表。
- 明确“逐项目导入”是**导入**语义：生成新 ID，不碰其他数据。
- 明确“灾难恢复”是**整库还原**语义：保留原 ID，只在 D7 规定的条件下可用。

## 9. engine.ts:385 写入了不带项目归属的系统模板（✅ 成立，并且发现一个现存缺陷）

**证据**
- `ensureSystemLeipzigStructuralProfileSeeded`（`engine.ts:385-402`）每次打开数据库时，都会写入 `structural_rule_profiles` 表一行 `scope: 'system'`、不带 `projectId` 的记录。
- 修订四要求目录表必须带归属，这会和这行系统种子冲突。

**新发现 N13（P2）**
- `claimUnscopedCatalog` 会把所有没有 `projectId` 的结构规则行都认领给第一个读取它的项目（`projectCatalogScope.ts:40-44`），**系统 Leipzig 模板也会被认领**。认领之后，其他项目看不到系统模板；删除这个项目时模板会被一起删掉，直到下次打开数据库重新写入。

**可以沿用的先例**
- ISO 639-3 种子已经是“代码里的静态数据加内存缓存”的做法（`iso6393Seed.ts:61-93`），从来不写进数据库。Leipzig 模板是唯一一个被写进数据库的系统数据。

**改动**
- 系统模板只放在代码里，不写进数据库。
- 列表查询时把系统模板和项目行合并展示；用户修改时，先“复制到项目”再改。
- 导出时过滤掉系统模板。

## 10. manifest 的 `bytes?` 是可选的，和“必须声明”矛盾；省略字节时 sha256/size 描述的是什么（✅ 成立）

**证据**
- 修订四 7.2 里 `files[]` 的 `bytes?: included|omitted` 是可选字段，而 4.2-7 要求每一行都必须声明。
- `files[]` 描述的是包里**实际存在的文件**。被省略的媒体在包里根本没有文件，所以它的 sha256 和 size 没有含义。

**改动**
- 按条目类型分别规定契约：
  - `files[]` 只列出包里实际存在的文件，sha256 和 size 描述的就是这个文件。
  - 媒体和附件放进 `entities[]`，必须写 `bytes: included|omitted`，以及原始内容的 `contentSha256` 和 `contentSize`（供 Relink 校验用）；`bytes` 为 `included` 时，再引用对应的 `files[]` 条目。

## 11. 批次依赖关系有误（✅ 成立）

**证据**
- 第 4 批的恢复导出要能“导入”，就依赖第 3 批的 JYB，还依赖第 5 点所说的转换器。修订四却写第 4 批只依赖 2A。
- 第 3 批的覆盖确认和 JYB 整库替换，需要用 2C 提供的 D6 判定函数。修订四却写第 3 批只依赖 2B。

**改动**
- 第 3 批依赖 2B 和 2C。
- 第 4 批中“原生快照 → JYB 转换”这部分依赖第 3 批；迁移框架本身仍然只依赖 2A。

## 12. 一刀切清空 localStorage 有风险（✅ 成立）

**证据**
- 修订四 8.1 的“需要的条件”写的是“清一次站点数据（8 个库加上 localStorage）”。D10 虽然写了“相关的 localStorage 键”，但没有列出具体是哪些。
- 全仓有 58 个文件使用 localStorage，其中包括 AI 设置、界面偏好等和项目数据无关的内容。
- voice sessions、user behavior、声学缓存这几个库也和项目数据无关。

**改动**
- 重置范围收窄为五个库：主库、迁移前备份库、`jieyu_recovery`、`jieyu-project-memory`、`jieyu_collab_client_state`。
- 只清除明确列出的 localStorage 键（见修订五 8.1），其他一律保留。
- 声学缓存可以按需单独清理，因为可以重新生成。
- 修订四 8.1 第 5 步要把“其他 IndexedDB 库”的 schema 历史也压成 `version(1)`，这一步还有一个隐患：对于**保留下来**的库，如果声明的版本号低于已经安装的版本，Dexie 打开时会抛出 VersionError。所以只有确实被删掉、重建的库才能重置版本，保留的库要沿用原来的版本历史。

## 13. 冻结点的定义（◐ 部分成立，需要用户决定）

**评审建议**：改为“首次需要保留有价值的数据，或首次交给非开发者使用，以先到者为准”。

**判断**：这个建议有道理。开发者自己做真实标注、准备长期保留时，就已经需要迁移安全了，而 D13 的“首次田野采录”可能来得更晚。

**处理**：但这会改变用户已经做出的决定 D13。修订五把它记为**提议修订 A1，等待用户确认**，在用户确认前 D13 仍然有效。
