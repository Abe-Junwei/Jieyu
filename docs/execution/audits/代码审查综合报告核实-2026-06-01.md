## 二、主题 1 — 「虚假安全感」核实

### 1.1 architecture-guard && 短路

| 项 | 结论 |
|----|------|
| **指控**（原报告原文） | 「architecture-guard **聚合链**在 core 失败处 `&&` 短路了，后 6 道守卫不执行」 |
| **核实** | **属实（现象成立；机制定位需精确化）** |
| **证据** | `package.json` 的 `check:architecture-guard` = 7 个子命令的 shell `&&` 串联（`check:architecture-guard:core && check:doc-code-symbol-parity && check:timeline-single-host-entry && ...`）。当 `:core` 因 `sessionMemory.ts` 超限失败时，后 6 道守卫（doc-code-symbol-parity / timeline-single-host-entry / fire-and-forget-governance / …）**确实不执行**——虚假安全感现象成立。`scripts/check-architecture-guard.mjs` **脚本内部**采用 `for...of` 无 `&&` 短路（局部 `&&` 仅为条件判断），故短路发生在 **shell 聚合层**而非脚本内部。 |
| **修正口径** | 原报告用词「聚合链 `&&` 短路」准确（指 `package.json` shell 串联）；本核实初稿曾误记为「脚本内部 `&&`」并据此判「不属实」，系稻草人，已订正。结论：**属实**，修复方向（聚合改 `;`/汇总，不让单点失败掩盖其余守卫）有效。 |

## 三、主题 2 — Worker/资源生命周期核实

### 3.1 C1 WorkerPool 双重派生 + registry 不清理

| 项 | 结论 |
|----|------|
| **指控** | WorkerPool.register() 内部再调用 factory()，与业务层预先创建的 Worker 形成双重派生；managedWorkerRegistry 永不删除终止条目 |
| **核实** | **属实** |
| **证据** | `src/workers/WorkerPool.ts:64`：`register()` 内执行 `const worker = factory()`。业务层在调用 `register()` 前已通过 `createManagedBrowserWorker()` 创建了实例 A（EmbeddingRuntime:171、AcousticAnalysisService:528、WhisperXVadService:100）。结果：实例 A 被业务使用，实例 B 被 Pool 管理但从未使用，成为孤儿 Worker。`src/observability/managedWorkerRegistry.ts:57-62`：`markManagedWorkerTerminated` 只改 `state = 'terminated'`，无 `entries.delete(id)`。生产代码永不清理。 |
| **影响** | 每次 VAD/声学/Embedding init 泄漏 1 个 Worker + 1 个 registry 条目。长会话累积。 |

### 3.2 C4 Embedding mid-flight terminate()

| 项 | 结论 |
|----|------|
| **指控** | Embedding 因 deps 不稳 mid-flight terminate()，嵌入随机失败 |
| **核实** | **部分属实** |
| **证据** | `src/hooks/ai/useAiEmbeddingState.ts:218-229`：effect cleanup 调用 `embeddingService.terminate()`。deps 为 `[embeddingSearchService, embeddingService]`。`src/pages/TranscriptionPage.AnalysisRuntime.tsx:24-31`：`createDeferredEmbeddingRuntime` 被 `useMemo` 包裹，deps 为 `embedding.provider.config.embeddingProviderConfig`。若配置对象引用不稳定，`useMemo` 重新执行 → 返回新 service 实例 → `useAiEmbeddingState` deps 变化 → cleanup 中 terminate()。`DeferredEmbeddingRuntime.terminate()`（`src/ai/embeddings/DeferredEmbeddingRuntime.ts:61-67`）级联 reject 所有 pending 请求。 |
| **条件** | 需要 `embeddingProviderConfig` 对象引用不稳定才会触发。若父组件稳定传递同一引用，则不会触发。 |

### 3.3 C5 声学 decode 无大小门控

| 项 | 结论 |
|----|------|
| **指控** | 声学分析在 decodeAudioData 前无大小门控，超大音频 OOM tab crash |
| **核实** | **属实** |
| **证据** | `src/services/acoustic/AcousticAnalysisService.ts:275-316`：`analyzeMedia` 中先 `fetch` 完整文件 → `arrayBuffer()` → `decodeAudioData()`，**无任何前置大小/时长检查**。唯一的 `MAX_EXTERNAL_PROVIDER_PCM_BYTES = 64MB` 检查在 `dispatchToWorker`（388 行）和 `performAnalyzeAudioBuffer`（408 行），均在 decode **之后**。对比 `src/services/vad/VadMediaBackend.browser.ts:93-103`：VAD 在 decode 前设置 `VAD_AUTO_WARM_MAX_BYTES = 100MB` 门控。 |
| **风险等级** | Critical：用户上传超大音频可直接导致浏览器标签页 OOM crash。 |

### 3.4 C7 声学 dispose race → 幽灵 fresh 缓存

| 项 | 结论 |
|----|------|
| **指控** | dispose() 不阻止后续 setCached，race 后产生幽灵 fresh 缓存 |
| **核实** | **属实** |
| **证据** | `src/services/acoustic/AcousticAnalysisService.ts:646-655`：`dispose()` 清除内存 cache 和 pending，但**无 disposed 标志**阻止后续写入。`runCachedAnalysis:341-370` 中 `task` 在 `runner(options)` 完成后调用 `this.setCached()`。若 dispose 发生在 runner 执行期间，runner 返回后仍继续 setCached。`AcousticAnalysisCacheDB.ts:81-117`：`put()` 无条件写入 `status: 'fresh'`。 |
| **风险等级** | High：dispose 后用户看到"分析已取消"，但缓存中残留 fresh 条目，下次读取可能拿到不完整/错误结果。 |

### 3.5 H5 MediaStream 异常路径不释放

| 项 | 结论 |
|----|------|
| **指控** | MediaStream 在异常路径不释放，麦克风灯长亮 |
| **核实** | **部分属实** |
| **证据** | `src/hooks/media/useRecording.ts:70-124`：`getUserMedia` 成功后，若 `new MediaRecorder` 或 `recorder.start()` 抛异常，catch 块**未执行 `streamRef.current?.getTracks().forEach(track => track.stop())`**。`src/services/VoiceInputService.recording.ts:55-89`：同理，`getUserMedia` 成功后后续步骤失败，`this.mediaStream` 未在 catch 中释放。正常路径和 dispose 路径的释放逻辑完整。 |
| **条件** | 仅当 `getUserMedia` 成功但后续初始化失败时触发。正常录音流程和显式停止流程无泄漏。 |
