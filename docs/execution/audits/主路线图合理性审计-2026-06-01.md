# 解语主路线图合理性审计（2026-06-01）

> **审计目标**：评估 `docs/execution/plans/解语-主路线图-master-roadmap-2026-06-01.md` 的规划本身是否合理、是否符合代码实际落位情况、是否存在不可执行的假设或系统性低估。
> **审计方法**：以 `docs/architecture/仓库现状与代码地图.md`（2026-05-13）为现状真源，交叉核对路线图中各切片的锚点声明、粒度估算、依赖关系与 DoD；辅以代码 grep 与关键文件读取。

---

## 一、总体结论：路线图方向正确，但存在结构性低估与命名漂移

| 维度 | 评级 | 说明 |
|------|------|------|
| **North Star 定位** | ✅ 合理 | 与代码实际（本地优先、桌面浏览器、转写主线、语言资产侧线）完全一致 |
| **Stage 划分** | ✅ 合理 | A→B→C 的「稳主线→开占位→对外」顺序与代码现状匹配 |
| **代码事实校准** | ⚠️ 部分准确 | 2026-06-01 修订已修正 B1/B2/B3 状态，但仍有过时命名（A1） |
| **切片粒度估算** | ❌ 系统性低估 | Stage B 多切片标 L≈2d，但子计划真源显示需 1–2 周；B4/B5 尤其严重 |
| **依赖关系** | ⚠️ 基本合理 | B2 作为「地基」的必要性被夸大；B3 已落地且未消费 B2 |

| **工程风险覆盖** | ❌ 遗漏 | 未反映代码治理计划 v2 中 🔴 controller 阈值逼近、F4 Batch B/C 活跃等持续风险 |

**一句话判断**：该路线图作为「优先级与依赖序」的框架是合格的，但作为「可执行排期」使用时，Stage B 的粒度必须重新校准，否则将在 B4/B5 遭遇严重进度击穿。

## 二、假设与代码事实一致性审计

### 2.1 A1 ReadyWorkspace 合同化 — 命名漂移

**路线图声明**：锚点包括 `computeReadyWorkspaceSurfaceProps`、`useReadyWorkspaceSurfaceProps.types`。

**代码事实**：
- `computeReadyWorkspaceSurfaceProps`：❌ 不存在（全仓库 grep 无命中）。
- `useReadyWorkspaceSurfaceProps.types`：❌ 不存在。
- 实际存在的是 `readyWorkspaceSurfacePropsAssemblyPhase.tsx`（350 行）、`useReadyWorkspaceSurfaceProps.tsx`（507 行，ratchet 650）、`buildReadyWorkspaceViewModelsSurfacePhaseParams.ts`（456 行）等。

**审计意见**：路线图沿用了已废弃的命名。ReadyWorkspace 编排壳的拆分工作（ARCH-7）在代码治理计划 v2 中已详细记录，路线图不应再引用不存在的文件名。建议将 A1 锚点更新为治理计划 v2 §5.1.1 的事实记录，或直接取消 A1 作为独立切片（因为 ARCH-7 已在代码治理计划中持续跟踪）。

### 2.2 B2 跨页刷新事件合同 —「零消费方」判断准确

**路线图声明**：「合同已落地·未接线」「零生产消费方」。

**代码事实**：
- `appShellEvents.ts`：事件合同 v1 + `dispatch/subscribeWorkspaceEvent` 原语 + 类型安全 + 92 行测试 — ✅ 存在。
- 全仓库（除 `appShellEvents.test.ts` 外）`dispatchWorkspaceEvent` / `subscribeWorkspaceEvent` 调用数：**0**。
- `WORKSPACE_UNIT_UPDATED_EVENT` 等常量在 pages 目录外消费数：**0**。

**审计意见**：路线图对 B2 的判断完全准确。这是一个「基础设施已铺好但无人使用」的典型切片，优先级应低于 B3 回归，与路线图调整一致。

### 2.3 B3 词典三栏联动 —「基本落地」判断准确，但粒度缺失

**路线图声明**：「基本落地·待回归」；列表/检索 + 详情(义项/词形/笔记) + 命中语段 + 深链跳转 + sessionStorage 态。

**代码事实**：

- 但**仍为只读浏览**，无编辑能力（与仓库现状文档一致）。

**审计意见**：路线图对落地程度的判断准确，但标为「—」（无粒度）不合理。B3 剩余工作主要是补 e2e/vitest 回归测试（S 或 M 粒度），而非 L。当前粒度缺失会导致排期模糊。

### 2.4 B4/B5 占位页 —「确认占位」判断准确

**代码事实**：

**审计意见**：路线图对占位状态的判断准确。但问题出在**粒度估算**（见 §三）。

### 2.5 A4 AI agent-loop flags —「基础 loop=on、3 flag 默认 off」准确

**代码事实**：
- `featureFlags.ts`：`aiChatAgentLoopEnabled: true`（基础 loop on）。

**审计意见**：路线图声明准确。但 A4 切片标 M（~1d）可能偏乐观——flag 切默认不是简单改 `true`，而是需要「验证后」切换，涉及 spec 测试 + agent-evals + e2e 全链路验证。

### 3.1 严重低估项分析

**B4 标注页 MVP**：
- 路线图标 L≈2d，目标是「token POS/gloss 最小编辑→统一写链路→转写页可见」。
- 子计划真源（标注页与词典页路线图）中，M1a（gloss/POS/保存/键盘/播放）+ M1b（morpheme/手动分词/词典链接编辑/Validator 模板）预计 **1–2 周**。
- 当前 `AnnotationPage.tsx` 是纯占位（25 行），需从零构建：页面壳、IGT 布局、行内微波形、键盘状态机、Leipzig 验证、保存链路、i18n。
- **2 天仅够完成页面壳 + 列表渲染 + 最基本编辑框，无法达到 DoD 要求的「写→reload→readback」闭环。**

**B5 语料库 P0**：
- 路线图标 L≈2d，目标是「多选成可见工作集；复制 text/plain + markdown」。
- 子计划真源（语料库产品定位与执行方案）中，语料库 P0 涉及：工作集数据模型、多选交互、出站序列化、可追溯元数据、与转写/标注的深链对齐。
- 当前 `CorpusLibraryPage.tsx` 是纯占位（25 行），且 `corpusLibraryLabEnabled: false`。
- **2 天无法完成从占位到可交互工作台的跳跃。**

**建议**：B4/B5 的粒度应改为 **XL（~1–2w）** 或拆分为多个 M/L 子切片，并与子计划真源的里程碑（M1a/M1b、P0-4）对齐。

> **【订正 2026-06-01】初稿本节自身存在「范围错配」，量级被夸大：**
> 1. **B5 预算误植**：初稿把「2–3 周」扣到 B5＝P0-4 单项上。核对 [三页联动计划书](../plans/三页联动最小落地计划书-2026-04-22.md) §4 原文「**P0（必须先做）预计周期：2-3 周**」——这 2-3 周覆盖 **P0-1 至 P0-6 全部六项**，P0-4 仅其一，约数天，**非 2-3 周**。量级夸大约 5×。
> 2. **B4 参照系错配**：初稿用「标注页路线图 M1a/M1b（完整里程碑，1-2 周）」量 B4，但 roadmap 的 B4 锚的是三页联动 **P0-3「标注页 MVP 壳」（最小 POS/gloss 编辑）**，远窄于 M1a/M1b。用大里程碑量窄 MVP，自然显得「严重低估」。
> 3. **结论修正**：B4/B5 单切片 2d 确实偏乐观（占位 25 行→可编辑工作台不可能 2d 装完），但应**拆分**而非标 XL：master roadmap 已据此拆为 **B4a（壳+gloss/POS，L）+ B4b（morpheme/分词/Validator，L）**、**B5a（工作集+多选，M）+ B5b（text/markdown 出站，M）**，每子片符合「功能切片 0.5–2d」口径。原「❌❌ 严重低估」降级为「⚠️ 低估」。

## 四、依赖关系与优先级审计

### 4.1 B2 作为「地基」的必要性被夸大

**路线图声明**：「B1（深链，部分✓）+ B2（事件合同，合同✓/未接线）是 Stage B 地基；B4/B5 占位页开放时接入二者。」

**代码事实**：
- B3 词典三栏联动已落地，且**未消费 B2 事件**（零消费方）。
- B1 深链已部分落地（LexiconPage 已使用深链跳转）。

**审计意见**：B3 的落地证明「深链」可以独立工作，「事件合同」并非所有 Stage B 切片的硬依赖。B2 的接线应作为「增强」而非「地基」来对待。路线图当前将 B2 设为地基，可能导致 B4/B5 被不必要地阻塞。

**建议**：将依赖关系调整为：
- B1 深链 = 软地基（推荐接入，但非阻塞）。
- B2 事件 = 增量增强（B4/B5 可先开放，后补事件驱动刷新）。

### 4.2 Stage A 与 Stage B 的并行性

**路线图声明**：「Stage A 与 Stage B1/B2 可并行（不同代码域），但触碰转写内核的 A 切片优先稳定。」

**审计意见**：合理。A2/A3（声学）与 B1/B2/B3（词典/深链/事件）确实是不同代码域，可并行。A5（时间轴）触碰转写内核，应优先。

### 4.3 C4 协作云独立性

**路线图声明**：「C4 协作云为独立切片，不阻塞本地闭环。」

**审计意见**：合理且必要。本地优先定位下，协作云不应成为任何本地切片的落地门槛。

## 六、遗漏项与风险审计

### 6.1 未反映代码治理的持续风险

代码治理计划 v2（2026-05-06）是当前活跃的工程治理真源，其中包含：
- §10.1：12 个命名 page controller 逼近或超过阈值（🔴 7 个 / 🟡 5 个）。
- §3.2：F4 Batch B/C 仍在活跃（高风险写入口 sandbox、证据面扩展）。
- §〇 P1：G4 `useAiChat` 瘦身（564/1100，近顶前需预拆）。

**主路线图完全未提及这些工程约束**。如果 Stage B 大切片（B4/B5）启动，向现有转写内核注入新逻辑，极有可能触发 architecture-guard 硬失败。

> **【订正 2026-06-01】上述「🔴 7 个 controller、98%/97%」数字来自治理文档，非实时守卫，须以 guard 输出为准：**
> 实时跑 `npm run report:architecture-hotspots` / `check:architecture-guard` 当前仅报 **1 个 hotspot**（`TranscriptionPage.ChatWindow.tsx` 766/800＝96%）+ **1 个硬失败**（`src/ai/chat/sessionMemory.ts` 1155/1000 超限）；**无任何 controller 报 97-98%**。原因是这些 controller 的 ratchet 已被抬高到「现状值」，当前用量在抬高阈值下「合规」（即另一独立问题：ratchet 现状化）。
> 因此本节**风险方向成立**（向逼近阈值/已抬高 ratchet 的 controller 注入逻辑确有破阈风险），但**具体百分比不可信**——code-governance-plan-v2 已被证明部分过时（如 Wave 4 假打勾、`db/types.ts` 标 14 行实为 1350 行）。**B4/B5 工程门槛应以实时 guard 输出取数，勿引用治理文档的历史百分比。** master roadmap §2 已据此把门槛改为「启动前跑实时 guard + 用独立 controller」。

**建议**：在路线图 §2 依赖硬约束中增加「工程治理门槛」——B4/B5 启动前，需确认目标复用链路上的 controller/hook 未超过 guard 阈值。

`featureFlags.ts` 中已有 `corpusLibraryLabEnabled: false`，但路线图 B5 未引用此 flag。建议统一。

### 6.3 分析页 B9 的处理

**审计意见**：合理。分析页方向未定，维持占位是审慎决策。
