# ADR 0091：字段修订、诊断补交与后续里程碑合同

## 状态

accepted。用户 2026-10-26 确认后续 M 的操作取舍。字段对照、诊断库复用和三平台文件原语的核对写在 [后续里程碑规格](../execution/specs/remaining-milestones-contracts/design.md)。本篇不改 ADR-0085、ADR-0087、ADR-0088、ADR-0089、ADR-0090 的正文。与那些篇冲突的句子以本篇为准。本篇不改产品代码，也不把未实施的切片记成完成。

## 背景

ADR-0085 把一次业务写入收成项目库里的一个事务，并要求新路径上「审计失败仍留下产物」改成整次回滚。本机诊断实际写在另一份 userData SQLite。两个独立连接不能当成一次原子提交。领域边界规格因此留下「诊断可丢还是必达」的草案。

备注、转写接受、删除准入、文件清除和备份快照也各有反例：整行旧快照会盖掉后来的字段；映射变化后接受会落到用户没看过的位置；删除等待期间又能启动新工作；垃圾箱调用开始后，再查一次数据库仍挡不住已经发出的文件操作。

## 决策

1. **冲突单位是声明过的字段，不是整行。** 提交只带改过的字段、读取时的修订号和新值。修订号在值真的变化时单调增加；改过又改回原值仍算冲突。一笔里任一字段冲突，整笔不提交，草稿保留。不同字段可以合并后再做整条校验。撤销只核对这些字段仍停在当时的修订，再写回改前值。不加无条件覆盖开关。不提交整行旧快照。

2. **研究内容与补交依据同事务，诊断库另收。** 项目事务里同时写入内容变更和一条待补交记录。这一步失败则内容和补交依据一起回滚。随后由宿主向 userData 幂等插入。诊断库失败或进程在确认前崩溃时，内容保持已提交，界面标明日志待补交，只重试日志，不重写内容。相同交付身份和相同载荷视为已接收；相同身份不同载荷是冲突，不覆盖。文稿清除不级联这些补交记录。这收窄 ADR-0085 里「审计失败整次回滚」的适用范围：解释这次写入所必需的项目内记录仍随内容回滚；另一份库里的技术日志不把已提交内容说成未保存，也不把操作显示成全部完成。不使用 ATTACH 把两个库绑成一个生命周期。不恢复通用工具审计表。

3. **备注有归属、锚点和附着状态。** 项目或文稿内容备注的归属在创建时由主进程核对并保存，不在目标消失后再反查。锚点是严格类型，不用一个 `targetId` 兼代所有目标。词条和义项备注只留在 `jieyu_json`，不在 `notes` 再存一份。译文正文和针对译文的评论分开。分析恢复只恢复关联资格，不覆盖后来改过的备注正文或分类。九类旧目标的去向和已核对的构造点以规格为准。当前 `notes` 行只有 layer/unit/token/morpheme 和单字符串 `body`，不能直接当作这个合同的载体。

4. **转写接受认预览凭据。** 映射变化后保留模型结果，按新映射重新预览，用户确认新位置后才能接受。接受在一次项目事务里写入正文、位置、来源、计数和一条不含待审正文的接受事实。同一运行里的同一候选不能靠更换操作编号再接受一次。响应丢失时只读查询该次接受是否已经提交，不自动再写。进程崩溃后内存候选不再存在，未处理计数清零并记为放弃；待审正文不写入运行记录、诊断或快照。ADR-0057 第 8、9 条继续有效。

5. **删除前先限制新工作。** 标记删除之前，目标范围进入短期 closing：拒绝新的普通写入和新任务。只允许这次协调里的草稿保存。保存失败或停止失败就退出并解除限制，已经保存或已经停止的结果保留。提交删除后刷新视图，再解除限制。进程重启后临时限制消失，已提交的删除状态仍在。生命周期、分析代际、时间映射修订和字段修订各管各的凭据，不用一个全局版本废掉无关编辑。

6. **文件清除按阶段，备份按快照保留文件。** 尚未调用系统垃圾箱时，恢复可以在同一事务里取消清除意图。调用已经开始则显示处理中，不报告恢复成功，也不排队自动恢复。失败和未知保留可处理身份，不按路径缺失猜成功。同一项目里的录音和附件不按各自引用计数单独决定能否移走同一路径。完整备份先取数据库一致快照，再按该快照的文件清单复制字节；复制期间这些文件不能进入垃圾箱调用。新包校验发布成功后才轮换旧包。不把 `project.sqlite` 文件本身当成 JYM 合同。

7. **恢复副本不继承执行资格。** 旧任务、旧审批和未完成的清除意图只作历史。唯一自动续做的是诊断日志补交：按原交付身份去重，并记下恢复来源，不重放研究内容。包模式决定身份映射和是否包含字节；普通文稿交换排除已删除正文。覆盖不能假定一次目录改名在三个平台上都原子替换非空目录。

8. **冻结和退出看完整协议与真实入口。** D14 冻结的是能解释项目的 DDL、JSON 载荷版本、身份与引用、字段冲突规则、文件布局和操作进度、包模式以及诊断交付身份。打开不兼容项目就拒绝。旧路径退出按生产界面、工具、后台、导入导出、备份、脚本和测试的替代矩阵，不按「已经没有 Dexie import」判断。

9. **实施顺序。** 先用来源这一个域验证字段修订和诊断补交，再做备注载体。不要求整个 M5-E 先做完。删除入口仍等 D1 与 D2 一起验收。本篇不授权开始这些产品改动。

## 被放弃的备选方案

1. 两个编辑者都提交整行旧对象，后写入的整行获胜。
2. 诊断库写失败就把已提交内容显示成未保存，并让用户重试整次修改。
3. 用 ATTACH 把项目库和 userData 合成一个事务。
4. 把九类备注都塞进现有 `notes.target_id` 加单字符串正文。
5. 在垃圾箱调用前再查一次数据库，把这个空隙当成已经互斥。
6. 直接复制正在使用的数据库文件，或用数据库备份成功代替音频和附件已进包的证据。
